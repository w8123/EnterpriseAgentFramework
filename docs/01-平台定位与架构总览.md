# 平台定位与架构总览

> 产品框架（定位、用户、核心对象、模块边界）于 2026-10-17 经用户确认，是后续各模块重设计的依据。模块重设计不得与本页冲突；需要改变本页结论时，先改本页并与用户确认。

## 平台定位

ReachAI 让 Java 企业系统把已有的业务操作开放给 AI，并以受治理的方式交给 Agent 在业务现场使用。它不是单纯的 Workflow Builder，也不是只做历史项目扫描生成 Tool 的工具，而是围绕企业能力发现、注册、资产化、编排、执行、治理和开放形成一条可追踪的生产链路。

- **解决的问题**：企业系统里大量业务操作只能由人点页面完成，AI 无法安全、可审计地调用它们。
- **核心价值链**：接入业务能力，编排成 Workflow，组装成 Agent，嵌入业务系统给业务用户使用，全程可追踪、可治理。
- **不做什么**：不做通用聊天产品，不做低代码业务系统，不替代业务系统保存业务主数据，不自建第三套能力或 Tool 资产。不做 Agent 大脑：Agent 循环复用开源 harness（嵌入式对话用 AgentScope，员工自己的 Codex / Claude Code 作为客户端接入）。

### 产品方向（2026-10-24 用户确认）

ReachAI 是开源项目，定位为**企业系统的 AI 操作层**：让任何 AI（业务系统里的嵌入式对话、员工自己的 Codex / Claude Code）都以员工本人的身份安全地操作企业业务系统，写操作可审批、全程可审计，好的做法沉淀为 Skill / Workflow 复用，管理者能看到使用记录。

- **三个入口，一套治理**：嵌入式对话（业务用户）、MCP（员工自己的 AI 工具）、AI Coding 任务（开发者的 Codex 改造业务系统）共用能力目录、员工身份、调用权限、写操作审批、审计 / Trace 和经验沉淀。
- **员工身份**：ReachAI 统一管理和同步员工账号（没有就新建），starter 改造业务系统身份代码，把 ReachAI 带来的员工还原成业务系统登录人。员工不需要理解 MCP，也不去业务系统点授权，只在页面上勾选要接入的系统（2026-10-24 用户修正）。
- **路线顺序**：① 员工在自己的 AI 工具里办业务（芋道验收）② MCP 写操作审批 ③ 运行记录一键沉淀为 Skill / Workflow，Skill 可导出为标准 SKILL.md ④ 管理者按人、AI 工具、业务系统查看使用记录 ⑤ Codex 经 AI Coding 任务改造业务系统。贯穿：10 分钟一键上手（ReachAI + 芋道 demo）和测试 / CI。
- **冻结**：A2A 互联中心、MCP 入向（M2/M3）、Kubernetes Managed Executor、Workflow 画布新功能、全站 UI 打磨。API 市场和 Skill 包保留，Skill 包强化为对外分发的经验载体。

详见[产品方向：企业系统的 AI 操作层](./plans/产品方向-企业系统的AI操作层.md)。

## 用户

开发人员、运营人员、管理人员在管理端工作；普通用户（业务系统员工）不进管理端，用业务系统账号在嵌入式对话或自己的 AI 工具里办业务。

| 用户 | 平台角色 | 在哪里 | 核心任务 |
| --- | --- | --- | --- |
| Java 接入开发者 | 开发人员 `DEVELOPER`，按项目授权 | 业务系统代码 + 管理端 | 用 SDK 声明业务方法和 API，处理变化评审（[专项基线](./plans/业务方法与API重构实施基线.md) U1、U3、U4）；Workflow、Agent、运行记录只读 |
| Agent / Workflow 实施人员 | 运营人员 `OPERATOR`，可直接发布 | 管理端 | 编排 Workflow、配置和发布 Agent、配置知识、MCP 员工可用发布和调用权限、看运行问题（U2、U4） |
| 管理者 | 管理人员 `MANAGER` | 管理端 | 看使用记录：谁、用什么 AI 工具、对哪个系统做了什么；必要时断开员工连接；其他只读 |
| 普通用户（业务系统员工） | 不是平台角色，由「调用权限」按业务系统角色控制 | 业务系统内的嵌入式对话，或自己的 Claude Code / Codex | 用自然语言办业务，管理自己的会话、记忆和 AI 工具连接 |

平台管理员 `PLATFORM_ADMIN`（账号与角色、认证源、模型、合规）是支撑角色，不单独设计产品主线。一个账号可以同时有多个角色；没有任何角色的账号登录管理端只看到「在业务系统里使用 AI 助手」的说明。角色只是权限码的组合，授权校验一律看权限码；平台权限（谁能在管理端做什么）和调用权限（普通用户能让 Agent 调用什么）是两套独立机制。页面上只读角色看不到写操作按钮，服务端接口仍逐个校验权限。详见[角色账号权限整理方案](./plans/角色账号权限整理方案.md)（2026-10-24，原「审计员」并入「管理人员」）和[人员、角色与权限重设计方案](./plans/人员角色与权限重设计方案.md)。

## 核心对象

产品只有一条主链：**项目**提供**业务能力**（Java 业务方法、HTTP API），**Workflow** 用 GraphSpec 编排业务能力，**Agent** 按用户意图选择已发布的 Workflow，再通过**使用入口**（嵌入式对话、MCP、A2A）交到用户手里。

支撑对象只服务主链，不脱离主链单独存在：

- **知识**（知识库、业务索引）服务于 Workflow 和 Agent 的检索。
- **记忆**（会话记忆、个人长期记忆）是 Agent 的一项能力，由 Agent 配置决定是否启用，见[记忆模块重设计方案](./plans/记忆模块重设计方案.md)。
- **运行中心**记录每一次执行：对话、运行记录、Trace、评测。排查主线是对话 → 出错的那一轮 → 运行详情定位失败节点 → 加入评测集 → 对比实验后再发布，见[运行中心整理方案](./plans/运行中心整理方案.md)。
- **自动化**定时运行 Agent 或 Workflow，管理计划和执行历史；在「运行与治理」组使用独立的「自动化中心」菜单入口（2026-10-19 确认独立入口，2026-10-20 恢复功能分组），执行结果仍可跳转运行中心查看。

## 模块边界

2026-10-20 用户确认恢复原有功能分组：智能化改造、AI 资产、运行与治理、平台资源。该决定替代 2026-10-17 的「开发 / 运营 / 平台管理」导航分组，不改变平台角色、权限码或项目授权范围。各菜单及子项仍独立按权限过滤，没有可见入口的分组自动隐藏；概览位于智能化改造组首项，按角色给出常用入口，「我的记忆」留在侧边栏底部的个人菜单。已退役的实验室不恢复。

导航分组只组织入口，各业务对象仍遵守唯一 owning service 和服务间 API 边界。MCP、A2A 的全局入口恢复到「集成与开放」，Agent 自身的嵌入与开放配置仍归 Agent。

| 导航组 | 分区 | 包含 | Owning service |
| --- | --- | --- | --- |
| 智能化改造 | 项目管理 | 项目、SDK 接入、同步诊断、页面动作；业务索引仍从项目详情进入 | capability（页面工作台由 control 承接） |
| AI 资产 | 业务能力 | Java 业务方法、HTTP API、变化评审 | capability |
| AI 资产 | Workflow | Studio、发布、调试 | runtime |
| AI 资产 | Agent | 配置版本、Workflow 白名单、记忆策略、嵌入与开放协议；Agent「嵌入」页集中配置可嵌入的业务系统、来源域名、令牌有效期、接入代码和嵌入会话（来源白名单数据仍按项目归属 capability） | runtime（开放入口经 control） |
| AI 资产 | Skill | 标准 Agent Skill 包管理 | control |
| AI 资产 | 集成与开放 / API 市场 | 外部 API 接入 | capability |
| AI 资产 | 集成与开放 / MCP Hub、A2A 互联中心 | 开放协议全局入口；对象配置仍回到所属 Agent | control（执行经 runtime） |
| AI 资产 | 知识库 | 知识库详情集中管理文件、检索测试、命中分析、设置 | knowledge |
| 运行与治理 | 自动化中心 | Agent / Workflow 定时计划、执行历史（独立菜单 `/automations`，按 `automation:read` 显示） | runtime |
| 运行与治理 | 运行中心 | 对话、运行记录、Trace、评测（一个菜单项，页签按权限显示；对话正文来自 control 的嵌入式对话事件，运行状态来自 runtime） | runtime（对话视图经 control 聚合） |
| 运行与治理 | 身份与权限 | 账号与权限、业务用户、认证源、调用权限、运行时用户映射；子项分别校验平台权限 | control |
| 运行与治理 | 合规 | 会话保留、Legal Hold、跨域数据擦除 | control 编排，各 owner 执行 |
| 平台资源 | 模型服务 | 模型中心、模型调试台 | model |

API 市场和标准 Skill 包继续保留（2026-10-18 确认），2026-10-20 按用户要求恢复至 AI 资产组；这次只调整导航，不新增调用能力。实验室（调用候选检索）已于 2026-10-18 删除：运行时不使用该检索，Agent 选择 Workflow 的排查看运行中心的运行记录和 Trace。文件入库和知识检索测试仍在知识库详情中，业务索引仍从项目详情进入，不恢复重复菜单。

## 当前技术主线

当前主线是业务系统通过 `reachai-spring-boot2-starter`、`reachai-capability-sdk`、`@ReachCapability` 和 `@ReachParam` 主动声明能力；平台侧形成能力快照、字段级 diff、评审、apply/ignore，并沉淀到 Capability Catalog；Workflow Studio 使用 `GraphSpec` 编排运行语义；Runtime Host 执行 Agent、Workflow、Trace、RunOps 和调试链路。

## 当前部署拓扑

第一阶段保持同一个 MySQL 库，不拆库。后端主路径已经进入物理服务拆分后的旧结构退场阶段，当前五个部署单元是：

| 部署单元 | 长期职责 | 默认端口 |
| --- | --- | --- |
| `reachai-control-service` | Platform Control public API/BFF，统一承接 `/api/**`、`/embed/**` 和 SDK 注册兼容入口 | `18603` |
| `reachai-runtime-service` | Runtime Host，承接 Agent、Workflow、GraphSpec、Trace、RunOps、调试和运行时内部 API | `18604` |
| `reachai-capability-service` | Capability Catalog，承接 SDK 注册、能力快照、diff/review/apply、扫描目录和能力资产 API | `18605` |
| `reachai-knowledge-service` | Knowledge / Retrieval，承接知识库、文件、Chunk、RAG、业务索引、向量检索和扫描器实现 | `18602`，context path `/ai` |
| `reachai-model-service` | Model Gateway，承接模型模板/实例、Chat、Embedding、Rerank（已删除 OpenAI 兼容 HTTP 代理入口） | `18601` |

旧 `ai-agent-service` module 已从仓库主路径删除，不再作为 Maven、IDEA、本地启动或部署单元存在。剩余兼容路径必须迁入 owning service 的本地实现，或作为明确兼容桥记录后正式退场。

服务职责、调用方向、配置和验证命令统一见 [五服务边界与本地启动](./architecture/service-boundaries.md)。本页不重复维护易漂移的完整接口清单。

## 前端入口

`ai-admin-front` 是管理控制台。浏览器请求一律先进 Control，由 Control 校验登录会话和路由权限后再转给 owning service：

| 前端路径 | 入口 | 后端归属 |
| --- | --- | --- |
| `/api/**` | `reachai-control-service` | 各 owning service |
| `/ai/knowledge/**`、`/ai/file/**`、`/ai/retrieval/**` | `reachai-control-service` 校验后转发 | `reachai-knowledge-service` |
| `/model/**` | `reachai-control-service` 校验后转发 | `reachai-model-service` |
| Runtime / Capability 健康状态 | 通过 `reachai-control-service` 的 `/api/internal-services/health` 聚合 |

前端不直接调用 `reachai-runtime-service:18604` 或 `reachai-capability-service:18605` 的内部端口。

## 运行语义

`GraphSpec` 是 Workflow 的可执行语义，`canvas_json` 只表示画布布局。新增 Workflow Studio 节点、AI 编辑能力或 Runtime 行为时，必须把可执行语义写入 Workflow `GraphSpec`，不能只修改前端画布表现。

Runtime 执行主线位于 `reachai-runtime-service`。Capability 资产与业务系统 SDK 注册主线位于 `reachai-capability-service`。知识检索、RAG 和向量能力位于 `reachai-knowledge-service`。模型调用统一经过 `reachai-model-service`。

当前主产品链路还包括：Control-owned 的项目/页面工作台、AI Coding Task Kernel、标准 Agent Skill 目录和 A2A Hub；Capability-owned 的 API 市场；Runtime-owned 的 EvalOps。这些扩展能力不改变五服务边界，也不重新引入第二套 Capability、Tool、Workflow 或 Agent 模型。

## 架构约束

- 公共 API 入口保持在 `reachai-control-service`，不要让前端重新认识旧大后端。
- 同库阶段仍要遵守服务表所有权和服务间 API 边界，不允许为了快速编译跨服务直接写对方表。
- 文档和产品口径默认使用 Capability / 能力。Skill 仅用于标准 Agent Skill 包或外部协议字段；不要重新引入自创的 Skill 业务资产模型。
- SQL 基线入口是 `sql/initV2.sql`；后续数据库变更按需新增 `sql/upgrade-*.sql`，确认并入基线后可清理历史升级脚本。
