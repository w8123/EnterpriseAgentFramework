# 平台身份与授权模型

> 状态：P3_ENTERPRISE_IAM_SOURCE_IMPLEMENTED / DEPLOYED_AUTH_E2E_PENDING（2026-08-27）

本文描述 ReachAI 当前已经存在的身份域、凭证边界和授权责任。源码事实入口是 Control 的 `identity` / `platform` package、Capability 的 `registry` package、Starter 的注册与 Embed client，以及 [Control API 认证边界矩阵](../architecture/platform-api-auth-matrix.md)。

## 当前结论

- 平台管理用户、业务系统应用、业务终端用户、协议客户端和内部服务是不同身份域，不能互相冒充。
- 平台角色是权限模板，服务端按权限码与作用域授权，不按“开发者/管理者”等角色名分叉后端。
- 建设中心和运营治理中心是产品工作区，不是新的身份域；工作区切换不能扩大权限。
- 管理端使用 Control 签发的可撤销不透明 Bearer session；当前真正可登录的 Provider 只有 `LOCAL`。
- 业务系统通过一次性 Enrollment Token 获得项目 `appKey/appSecret`，后续 Registry、Embed Token 交换和项目写入使用项目签名。
- 业务终端用户身份必须由业务后端从本系统登录态解析，再通过受签名保护的 Embed Token 交换交给 ReachAI；浏览器提交的 `principal` 不能自行成为可信身份。
- Runtime 和 Capability 只能使用上游已经验证并显式传递的身份。`/internal/**` 路径名、请求 metadata 或普通 JSON 字段本身都不构成认证。
- 源码和静态契约已核对；目标数据库升级、运行进程、真实登录、角色隔离和业务 Embed 浏览器链路仍应分别验收。

## 身份与凭证域

| 身份域 | 代表谁 | 当前凭证 | 主要入口 |
| --- | --- | --- | --- |
| 平台管理用户 | 配置和治理 ReachAI 的人 | Control 不透明 Bearer session | `/api/platform/**` 及受保护管理 API |
| 业务系统应用 | 接入 ReachAI 的业务后端 | Enrollment Token；之后为项目 HMAC 签名 | `/api/registry/**`、`/api/embed/token/exchange`、`/api/knowledge-ingress/**` |
| 业务终端用户 | 业务系统中当前登录的人 | 短期 Embed JWT；Capability 调用时为 Invocation Token | `/api/embed/chat/**`、业务 Capability endpoint |
| AI Coding 客户端 | 获准改造某项目的外部 AI 工具 | 项目级 AI Coding key/task 凭证 | `/api/ai-coding/**`、Workflow AI Coding 路径 |
| MCP 客户端 | 外部 MCP consumer | MCP API Key | `/mcp/**` |
| 远程 Agent | A2A 调用主体 | A2A Principal 对应的协议凭据 | `/.well-known/agent-card.json`、`/a2a/v1/**` |
| 内部服务 | 五服务之间的可信调用方 | HMAC、nonce、时间窗、body 摘要和 TLS/mTLS 传输声明 | `/internal/**` |

平台 session 不能替代 MCP/A2A/Embed/SDK 凭证；项目签名也不能自动获得平台管理员权限。

## 平台管理身份

### 已实现接口

| 接口 | 作用 |
| --- | --- |
| `POST /api/platform/auth/login` | LOCAL 用户名/密码登录；认证后签发随机 session token |
| `GET /api/platform/auth/me` | 解析当前 session、角色、权限和 scope |
| `POST /api/platform/auth/logout` | 撤销当前 session |
| `GET/POST /api/platform/auth-providers` | 查询或保存 Provider 元数据；需要 `platform:admin` |
| `GET /api/platform/users`、`GET /api/platform/roles` | 管理用户与角色目录；需要 `platform:admin` |
| `GET/PUT /api/platform/users/{userId}/roles` | 读取或替换用户角色授权；需要 `platform:admin`，并保护全局管理员不变量 |
| `GET/POST/PUT /api/platform/account-management/users/**` | 企业账号目录、创建、资料/状态维护；需要全局 `platform:admin` |
| `POST /api/platform/account-management/users/{userId}/password-reset` | 仅重置 LOCAL 账号强密码，同时撤销全部会话 |
| `POST /api/platform/account-management/users/{userId}/sessions/revoke` | 撤销目标账号的全部有效会话 |
| `PUT /api/platform/account-management/users/{userId}/grants` | 使用 canonical 项目编码替换角色授权，并保护末位全局管理员 |
| `GET/POST/PUT /api/platform/account-management/roles/**` | 查询权限目录，创建或维护自定义角色；系统角色不可修改 |
| `GET /api/platform/account-management/audit-events` | 查询账号、角色、会话与授权管理审计；最多返回最近 500 条 |
| `GET /api/platform/business-users/**` | 查看业务用户目录和外部身份绑定；需要 `identity:business-user:read` |
| `PUT/POST /api/platform/business-users/**` | 修改业务用户和外部身份绑定；需要 `identity:business-user:manage`；它不是平台登录账户 |

核心表由 Control 拥有：

- `control_platform_user`
- `control_platform_role`
- `control_platform_user_role`
- `control_platform_permission`
- `control_platform_role_permission`
- `control_platform_login_session`
- `control_platform_auth_provider`
- `control_platform_auth_audit_event`
- `control_business_user`
- `control_external_user_binding`
- `control_external_user_role_binding`

浏览器只得到随机原始 token；`control_platform_login_session.access_token_id` 保存 SHA-256 摘要，可过期、撤销并重新解析角色/权限。不要把该 token 写进日志、截图、README 或脚本参数。

授权求值器识别 `GLOBAL`、`WORKSPACE`、`PROJECT` 作用域；当前角色管理入口只开放可验证的 `GLOBAL` 与 `PROJECT` 绑定。角色本身只是权限集合。`control_platform_role.role_kind` 明确区分由版本基线维护的 `SYSTEM` 角色和可由管理员维护的 `CUSTOM` 角色。当前系统角色模板、企业账号管理约束、P1 权限和未来工作区规则见 [平台授权与工作区底座](../architecture/platform-authorization-foundation.md)。前端菜单隐藏只是授权结果的投影，直接 URL 与 Control API 必须继续使用同一权限码独立检查。

### Provider 真实边界

当前版本只有 `LOCAL` 实现了认证。`HEADER`、`OIDC`、`SAML` 可以作为 Provider 类型元数据出现，但源码会拒绝把它们设为 `ACTIVE`，也会拒绝保存非空 Provider 密钥配置，直到加密存储和真实适配器实现。

本地开源模式默认：

```text
admin / admin123
```

这只用于首次体验，登录页会自动填充。已有管理员不会被 bootstrap 自动覆盖或改密。生产必须至少设置：

生产必须至少设置：

```powershell
$env:REACHAI_LOCAL_AUTH_ENABLED = 'false'
$env:REACHAI_BOOTSTRAP_ADMIN_ENABLED = 'false'
```

关闭 LOCAL 之前必须先部署并验证替代身份链路；当前源码尚不能把 OIDC/SAML/HEADER 写成“已可用”。

### 路由分类

`PlatformConsoleRoutePolicy` 将 Control Controller 映射划入四类：

- `PLATFORM_SESSION`：管理端 session + RBAC；
- `PUBLIC_LOGIN`：只允许登录入口；
- `INDEPENDENT_PROTOCOL`：Embed、AI Coding、MCP、A2A、Gateway、internal 等使用自己的凭证；
- `COMPATIBILITY_PENDING`：当前 `/api/registry/**` 的多凭证兼容域。

新增 Controller 路由必须进入唯一凭证域。未分类不等于匿名可用；`COMPATIBILITY_PENDING` 也不等于已经完成平台 session 与 SDK 签名的双重适配。

## 业务系统应用身份

### Enrollment 与项目凭据

1. 具有 `platform:admin` 的平台用户调用 `POST /api/platform/registry-enrollments`，得到一次显示、72 小时有效的一次性 Enrollment Token。
2. Starter 首次调用 `POST /api/registry/projects/register`，使用 `X-ReachAI-Registry-Enrollment-Token` 消费该 token。
3. Capability 创建项目主凭据并只在注册响应中返回一次 `appKey/appSecret`。
4. Starter 原子写入独立 credential store，随后从内存清除 Enrollment Token；Enrollment Token 不落入该文件。
5. 后续注册、心跳和能力同步使用 `X-ReachAI-App-Key`、`X-ReachAI-Timestamp`、`X-ReachAI-Nonce`、`X-ReachAI-Signature`。

项目、实例和凭据由 Capability 拥有，主要表为 `capability_scan_project`、`capability_project_instance`、`capability_registry_project_credential`。Control 只负责平台管理员入口和公共兼容边界，不直接读取或写入这些表。

Starter 默认 credential store 位于进程用户的 `~/.reachai/registry-credentials/<project-code>.properties`，也可用 `reachai.registry.credential-store-path` 指定。该文件含长期项目密钥，必须限制权限、纳入轮换和备份策略，并保持在应用包与 Git 之外。

### 项目签名约束

- `projectCode` 必须与凭据绑定项目一致；不能信任请求体自报的其它项目。
- 时间戳和 nonce 用于时窗、防重放；body-bound API 还签署方法、规范路径和精确 JSON body SHA-256。
- Control 需要验证项目身份时，应委托 Capability credential owner，再向 Knowledge/Runtime 传递验证结果。
- HMAC 不能替代 HTTPS/mTLS；生产内部和外部链路仍要验证传输加密。

## 业务用户与 Embed 身份

### Token 交换链路

```text
业务浏览器
  -> 业务后端（从本系统登录态解析当前用户）
  -> ReachAiEmbedTokenClient（项目签名）
  -> Control /api/embed/token/exchange
  -> Capability 验证项目凭据和 Embed policy
  -> Runtime 复核目标 Agent
  -> Control 签发短期 Embed JWT
  -> 浏览器创建 Embed Session 并发送消息
```

浏览器不得保存 `appSecret`，也不得把自己填写的 `externalUserId` 直接发给 ReachAI。业务后端应使用 `ReachAiCurrentUserProvider` 或本系统等价能力解析当前用户，然后构造 `ReachAiEmbedPrincipal`。完整 broker 示例见 [Spring Boot Starter README](../../reachai-spring-boot2-starter/README.md)。

Embed JWT 当前使用 HS256 和 `kid`，至少绑定：

- `tenantId`、`appId/projectCode`、`agentId`
- `externalUserId`、`globalUserId`、`userName`、`roles`、`attributes`
- `pageKey`、`pageInstanceId`、`route`、`origin`
- `iat`、`exp`、`jti`

Control 创建 `control_embed_session` 时复核 token 与请求中的页面身份；消息、交互恢复和 Page Action 都继续限定同一 session、用户和页面实例。`control_business_user` 目录可用于治理和跨系统映射，但当前 Embed Token 交换不等同于自动创建平台登录用户。

## Capability 调用身份

Runtime 不向业务 Capability 转发浏览器原始 `Authorization`。Capability owning service 使用项目 `appSecret` 签发短期 `X-ReachAI-Invocation-Token`，包含项目、能力和已经验证的用户上下文；业务 Starter 在 `ReachCapabilityEndpoint` 前验签，并通过 `ReachAiInvocationContext` 暴露给业务代码。

业务服务仍必须执行自己的租户、角色、行级权限和数据脱敏。Invocation Token 证明请求来自 ReachAI 且携带了某个上下文，不替代业务系统对目标资源的最终授权。

## 授权责任

| 层 | 负责什么 | 不能假设什么 |
| --- | --- | --- |
| Control | 平台 session、RBAC、Embed/协议身份终止、跨服务编排 | 不能因同库直接读写 Capability/Runtime/Knowledge 表 |
| Capability | 项目凭据、签名验证、能力目录和 Invocation Token | 不能把请求体 `projectCode` 当成已认证项目 |
| Runtime | Agent/Workflow allowlist、执行身份、Guard 与证据 | 不能从 metadata 提升用户、tenant、role 或 scope |
| 业务后端 | 原始用户登录、tenant/row 权限、业务副作用 | 不能让浏览器自报 principal，也不能只信平台角色替代本地授权 |

`control_tool_acl` 已有管理和 explain 能力，但统一接入 Agent 装配、MCP 和所有协议执行仍未完成。文档不得把“表和管理页面存在”写成全链路强制授权已经完成。

## 尚未完成的门禁

- OIDC、SAML、HEADER Provider 的真实认证适配与加密配置存储；
- 组织、用户组、SCIM 生命周期同步、授权审批、周期性访问复核和审计外部归档；
- `/api/registry/**` 平台 session/SDK 签名双凭证的完整显式适配；
- Tool ACL、Guard、MCP、Gateway、A2A 的统一运行期策略闭环；
- Capability、Knowledge、Model、Context、MCP 等剩余管理域从粗粒度 `platform:read/write` 迁移到完整资源级权限矩阵；Agent、Workflow、Automation 与 RunOps 核心管理入口已完成领域权限和 PROJECT scope 源码收口，但旧 Eval opaque ID 仍按 GLOBAL-only fail-closed；
- 目标数据库升级、Control/Capability/Runtime 新制品重启后的登录与角色隔离；
- 外部业务用户独立完成 Token broker、Embed Session、Agent 对话、Page Action 和 Capability 行级授权的浏览器 E2E。

剩余认证实施与验收记录见 [平台认证整改计划](../plans/platform-auth-remediation-implementation-plan.md)。计划状态不能替代当前源码和部署证据。
