# ReachAI 全站 Glass Workbench 设计系统方案

状态：已确认

日期：2026-07-10

范围：`ai-admin-front` 管理端全站 UI 设计系统与分批迁移策略

## 1. 背景

ReachAI 已完成项目管理、项目详情、SDK 接入工作台等页面的局部 UI 优化，形成了浅色玻璃工作台的视觉方向，但全站尚未形成稳定、可复用、可验证的设计系统。当前主要问题不是缺少高质量单页，而是以下能力仍然分散在页面级实现中：

- 玻璃表面、背景光、边框、阴影和模糊配方。
- 表单、表格、弹窗、抽屉、向导和页面头的公共模式。
- 七套品牌换肤与浅暗主题的统一映射。
- 密度、交互状态、错误状态和响应式规则。
- Figma 与真实前端实现之间的同步闭环。

本方案在现有 [前端 Glass Workbench 设计系统与 UI 重构实施方案](../../reference/前端Glass-Workbench设计系统与UI重构.md) 基础上，将范围从局部样板页扩展为全站设计系统，并明确 Figma 与前端的协作边界。

Figma 文件：[Reach Ai](https://www.figma.com/design/dLSJOki5yBoBeEx2GEZHU5/Reach-Ai)

## 2. 已确认决策

### 2.1 产品方向

- ReachAI 是企业工作台型产品，不按营销页或展示大屏设计。
- 采用“先收口设计系统，再批量迁移页面”的长期一致性路线。
- 接入项目弹窗、Tool 向导、Agent 编辑页只是界面形态样本，不是全部优化范围。

### 2.2 Figma 与前端

- 采用混合路线：轻量 Figma 先行、前端组件化落地、真实交互稳定后回写 Figma。
- Figma 负责变量、组件和页面模式，不负责完整重画几十条业务路由。
- 前端负责真实数据、长文本、交互、错误、响应式与性能验证。
- Figma 与前端使用一致的语义命名，任何一方发生设计调整后必须回写另一方。

### 2.3 主题和品牌

- 浅色 Glass Workbench 为精修主体验。
- 暗色只要求完整可用，不进行同等程度的视觉精修。
- 保留现有七套品牌换肤。
- 默认主操作色不固定为紫蓝或蓝青，全部跟随当前品牌 Token。
- 状态色保持语义稳定，不随品牌色切换。

### 2.4 玻璃与密度

- 全站采用 C3“全域强玻璃”：页面头、卡片、表单、输入框、表格、弹窗和抽屉都具备明显的通透、光泽、模糊和层次感。
- 全域玻璃不等于所有嵌套节点都使用独立高光、边框和投影；同一视觉区域最多出现三层明显深度。
- 信息密度按场景自适应：
  - `compact`：表格、监控、审计、运行流水。
  - `comfortable`：普通列表、详情和配置表单。
  - `spacious`：接入向导、空状态和首次创建流程。

### 2.5 Studio 边界

- Workflow Studio 和 Agent Studio 保持独立画布布局。
- 本轮只让 Studio 消费统一 Token、基础表单控件、弹窗、抽屉、状态色和交互状态。
- 不将普通 Glass Workbench 页面头、侧栏或内容布局强行套入 Studio。

## 3. 设计目标与非目标

### 3.1 目标

- 相同组件、状态和交互在全站表现一致。
- 页面不再新增私有颜色、阴影、模糊或玻璃配方。
- 七套品牌只通过变量切换即可正确作用于全站。
- 新页面可以通过组合公共模式落地，不重新发明页面结构。
- 已优化页面逐步回归公共 Token 和组件，避免成为不可维护的视觉孤岛。
- 强玻璃视觉与高密度企业操作同时成立。

### 3.2 非目标

- 不更换 Element Plus，不引入第二套 UI 框架。
- 不在本轮重构 Studio 画布布局和节点交互。
- 不要求 Figma 覆盖所有业务页面和所有数据状态。
- 不为七套品牌分别维护页面级样式。
- 不把本轮 UI 设计工作扩大为无关业务逻辑重写。

## 4. 设计系统架构

### 4.1 品牌原语层

七套品牌分别提供以下原语，不直接描述具体组件用途：

- 主色、悬停色、激活色、选中色。
- 品牌 RGB 通道，供透明度组合使用。
- 页面背景光、品牌渐变和装饰色。
- 品牌柔和背景和高亮表面。

品牌原语只表达品牌，不表达成功、警告、危险等业务状态。

### 4.2 语义 Token 层

语义层将品牌、主题和密度映射为界面角色：

| 分类 | 语义角色 |
| --- | --- |
| 页面 | canvas background、ambient glow、decorative texture |
| 玻璃表面 | shell、panel、control、overlay、selected、disabled |
| 边界 | subtle border、readable border、focus ring、divider、inner highlight |
| 阴影 | card、floating、overlay、active、danger |
| 模糊 | surface blur、floating blur、overlay blur、fallback solid surface |
| 文本 | primary、secondary、muted、disabled、inverse、link |
| 状态 | success、warning、danger、info、neutral |
| 密度 | compact、comfortable、spacious 的控件高度、间距和区块内边距 |
| 动效 | fast、normal、slow、reduced motion |

前端使用 CSS Variables；Figma 使用 Variables、Modes 和 Styles。两端名称应保持可机械映射。

### 4.3 公共组件配方层

Element Plus 继续提供交互和可访问性基础，公共样式只消费语义 Token。页面不得针对 `el-button`、`el-input`、`el-dialog` 等组件重复定义品牌色、玻璃背景和投影。

公共组件只在存在清晰复用边界时创建，避免把每个 `div` 包装成组件。

### 4.4 页面模式层

页面只负责业务结构、数据流、网格、尺寸和响应式，统一复用以下模式：

1. 列表工作台。
2. 详情工作台。
3. 表单工作台。
4. 步骤向导。
5. 调试/测试台。
6. 监控与审计。
7. Studio 特殊画布。

## 5. 公共组件边界

### 5.1 页面结构

- `AppPageBackground`：品牌环境光、渐变和装饰纹理。
- `AppSidebar`、`AppBreadcrumb`：全局导航和定位。
- `PageHeader`：标题、说明、标签、状态、元信息和页面动作。
- `MetricStrip`：同一玻璃容器中的业务指标和分隔。
- `WorkbenchPanel`：页面主体容器，支持三档密度和明确表面层级。

### 5.2 数据工作台

- `FilterBar`：搜索、筛选、重置和查询操作。
- `DataTableShell`：表格头、工具栏、内容、空状态和分页。
- `StatusTag`：统一业务状态的颜色、图标和文案层级。
- `RelativeTime`：相对时间与绝对时间提示。
- `RowActions`：行级动作、溢出菜单、权限和危险动作。

### 5.3 表单体系

- `FormSection`：标题、说明、字段组和可选动作区。
- `AdvancedSection`：System Prompt、JSON、策略和低频配置折叠。
- `SecretField`：凭证遮罩、查看、复制、重新生成和安全说明。
- `CodeField`：代码、Prompt、Schema、JSON 的编辑容器。
- `FormActions`：取消、保存、下一步和保存草稿的统一行为。

### 5.4 浮层体系

- `AppDialog`：普通创建、编辑和确认。
- `WizardDialog`：步骤轨道、步骤校验、内容区和固定底栏。
- `AppDrawer`：详情、日志、规则、差异和低风险编辑。

浮层使用强玻璃表面，但正文和表单控件的对比度必须高于被遮罩的背景页面。

### 5.5 反馈与状态

- 加载骨架、空状态、成功结果、无权限和接口失败。
- 字段级、步骤级和页面级错误。
- 默认、悬停、聚焦、选中、禁用和加载交互状态。
- 向导的未开始、进行中、已完成、失败和跳过状态。

## 6. 页面模式

### 6.1 列表工作台

适用于项目、Tool、知识库、模型、用户、能力目录等页面。标准结构：

`PageHeader → 可选 MetricStrip → FilterBar → DataTableShell`

默认使用 `comfortable` 页面间距和 `compact` 表格密度。

### 6.2 详情工作台

适用于项目、知识库、文件、业务索引、RunOps 等详情页。标准结构：

`PageHeader → 状态/指标 → 业务分区 → 关联数据或时间线`

详情页不重复展示同一状态，不堆叠多个无业务价值的摘要卡。

### 6.3 表单工作台

适用于 Agent、认证源、模型配置和各类创建/编辑页。标准结构：

`PageHeader → FormSection 组 → AdvancedSection → 固定或页面底部 FormActions`

新建态和编辑态可以显示不同的右侧说明或检查区，但不能因新建态缺少数据而留下空白列。

### 6.4 步骤向导

适用于 SDK 接入、MCP 接入、页面助手、Tool 创建等流程。步骤轨道和底栏只能表达一种明确推进关系：

- 如果允许跳转，步骤项必须表达可访问、已完成或存在错误。
- 如果不允许跳转，步骤项仅作进度展示。
- “保存”“保存草稿”“下一步”“完成”必须语义不同，不能同时成为无解释的主操作。

### 6.5 调试/测试台

适用于模型 Playground、检索测试、Tool 测试、分类器测试和 Agent 调试。标准结构：

`输入/配置区 → 运行操作 → 结果区 → Trace/原始数据抽屉`

输入与结果应在固定层级中对照，运行中状态不得造成布局跳动。

### 6.6 监控与审计

适用于 RunOps、MCP 调用流水、A2A 会话、嵌入式会话和同步快照。默认 `compact` 密度，强调筛选、时间、状态和快速定位，不使用大面积无信息留白。

### 6.7 Studio 控件样板

Studio 复用主题、表单控件、弹窗、抽屉、状态和代码编辑外壳，但继续保留独立画布、节点、缩放和调试布局。

## 7. Figma 与前端协作

### 7.1 Figma 产物

现有 Figma 文件继续维护：

- Foundations：颜色、玻璃、边界、阴影、模糊、文字、密度和状态。
- Component Masters：公共组件及其必要变体。
- Pattern Frames：七种页面模式各一个标准 Frame。
- Existing Screens：已优化页面作为实际应用示例，不作为组件主定义。

业务页面只需记录采用哪种模式及有哪些特殊区块，不要求完整重画所有状态。

### 7.2 协作闭环

1. 在 Figma 中确认变量、组件或模式。
2. 在前端公共层实现，不直接进入业务页面写私有样式。
3. 用真实路由、真实数据和真实交互验证。
4. 如果实现因长文本、错误、响应式或性能需要调整，将结论回写 Figma 主组件。
5. 页面迁移只组合已确认的公共能力。

## 8. 迁移策略

迁移按公共能力覆盖率推进，不按菜单顺序逐页美化。

### Phase 0：现状盘点与契约冻结

- 建立路由到页面模式的清单。
- 标记现有公共组件、页面私有样式和硬编码玻璃配方。
- 冻结 Token 命名、密度语义和 Studio 边界。

### Phase 1：Token 与 Element Plus 映射

- 收口品牌原语、浅暗主题和语义 Token。
- 合并重复的 Element Plus 主题覆盖。
- 为不支持模糊和减少透明度场景提供实体表面回退。

### Phase 2：公共基础组件

- 页面头、指标条、工作台容器。
- 按钮、输入框、Tabs、状态、分页和交互状态。
- 普通弹窗、向导弹窗、抽屉和固定操作栏。

### Phase 3：数据页面

- 列表、筛选、表格、分页和空状态。
- 优先迁移覆盖页面最多的标准列表模式。

### Phase 4：详情与表单

- 详情模式、表单分组、高级配置、Secret 和 CodeField。
- 已优化项目页面回归公共 Token，删除页面私有材质配方。

### Phase 5：任务型工作台

- 向导、测试、调试、评审和 RunOps。
- 验证步骤、运行、错误、重试和结果状态。

### Phase 6：Studio 共享控件

- 只替换共享 Token 和基础控件。
- 不调整画布、节点编排和 Studio 页面结构。

## 9. 错误、安全、性能与可访问性

### 9.1 错误处理

- 字段错误贴近输入项。
- 步骤错误在步骤轨道和底栏汇总。
- 页面接口错误保留原结构并提供重试。
- 保存失败时保留输入，不自动关闭浮层。
- 空数据、无权限和接口失败使用不同组件和文案。

### 9.2 凭证安全

- App Secret、Token、AI Coding Key 等默认遮罩。
- 查看、复制、重新生成分别授权。
- 截图、日志和错误消息不得直接包含完整凭证。
- 复制后提供短暂反馈，不长期在页面保留明文。

### 9.3 强玻璃性能边界

- 只有容器层使用真实 `backdrop-filter`。
- 表格单元格和大量列表行使用预计算半透明表面，避免逐行实时模糊。
- 同一视觉区域不叠加超过三层实时模糊。
- 不支持模糊、低性能设备和减少透明度偏好使用实体表面回退。
- 动效只服务状态反馈和层级进入，不使用持续漂浮或大面积环境动画。

### 9.4 可访问性

- 正文、辅助文字、禁用态和状态色达到可读对比度。
- 焦点清晰，状态不只靠颜色表达。
- 纯图标操作具有 Tooltip 和 `aria-label`。
- 支持键盘完成主要任务流程。
- 验证 125%、150%、200% 缩放和窄屏重排。
- 暗色模式不得出现不可读内容、白底闪烁或状态丢失。

## 10. 验证与验收

### 10.1 技术验证

- `npx vue-tsc --noEmit`
- `npm run build`
- 公共 Token、工具函数和关键组件的目标测试。
- 现有 UI 检查脚本按迁移批次更新或补充。

### 10.2 视觉与交互矩阵

- 每种页面模式至少选择一条真实路由作为样板。
- 浅色完整验收，暗色兼容验收。
- 七套品牌执行 Token 和构建检查；视觉重点抽查三套差异最大的品牌。
- 覆盖正常、空、加载、错误、权限不足和长文本状态。
- 使用相同视口和状态进行参考图与真实页面截图对比。
- 验证主操作、Tabs、菜单、表单、弹窗、抽屉、分页和键盘路径。

### 10.3 完成定义

以下条件全部满足才视为设计系统阶段完成：

1. Figma 与前端语义 Token 一致。
2. 七种页面模式都有公共组件支撑和真实路由样板。
3. 本轮触及的页面没有新增私有颜色、阴影、模糊或玻璃配方。
4. 已优化页面也已回归公共 Token，不再依赖巨型页面级覆盖层。
5. 全域强玻璃具备可用的实体回退和性能边界。
6. 浅色、暗色、代表品牌、关键状态和响应式检查通过。
7. Studio 的共享控件正确跟随主题，但画布结构未被普通工作台样式破坏。

## 11. 后续交付物

本设计批准后，下一阶段应单独编写实施计划，至少包含：

- 路由与页面模式清单。
- Token 和公共组件的文件级改造顺序。
- 各迁移批次的真实样板路由。
- Figma Variables、Components 和 Pattern Frames 的对应任务。
- 每个批次的验证命令、视觉检查和回滚边界。
