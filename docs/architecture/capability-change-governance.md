# 能力变化的自动治理

2026-09-10 开发验证更新：独立的真实 Spring Boot 2 SDK 业务进程已通过平台注册、签名回调同步、只读能力自动接纳和重复内容去重。增加必填参数后，来源漂移先阻止调用；接受新契约后旧 MCP 发布继续拒绝，重新发布后按新 schema 调用成功。可信租户通过专门签名模式传到 SDK，机器主体不成为业务用户。25 张资产表清理回读一致，开发库对应升级已执行；下方 2026-09-05 的原始验收记录保留为历史。业务端签名追踪号现与平台 MCP 根追踪号一致，客户环境和完整浏览器验收仍待完成。详见 [真实 SDK 契约验收](../../output/tasks/architecture-audit-20260905/capability-tenant-scope-notes.md) 和 [SDK 追踪号验收](../../output/tasks/architecture-audit-20260905/sdk-trace-propagation-notes.md)。

## 产品目标

能力接入、更新和使用以自动处理为正常路径。使用者负责发现能力、编排与运行；项目负责人只处理系统无法确定的业务选择。快照和审计是证据，不是用户逐批清空的任务。

## 事实与职责

- Capability 保存来源观察、候选差异、已接受定义和决策记录，拥有自动接纳策略与调用前的一致性保护。
- Runtime 根据 Workflow 草稿、已发布版本和 Agent 当前配置提供真实引用证据。查询失败、文档无法解析或证据不完整必须标记未知。
- Control 保持平台会话、项目权限、操作人归属和 MCP / A2A 发布边界。目录接纳不改变调用授权或自动发布外部能力。
- 业务服务仍拥有实际实现。恢复目录不等于恢复业务代码；无法确认来源与已接受契约一致时，不继续调用已经漂移的接口。

## 处理规则

### 注册项目身份

`capability_scan_project.project_code` 的非 NULL 值由数据库唯一约束维护，是同库中稳定的项目身份；项目名称、首次注册令牌和接入环境不能形成第二个同编码项目。注册入口复用 `RegistryEnrollmentService.normalizeProjectCode`，与令牌绑定采用同一规范化规则。

单个令牌消费锁防止同一令牌重复使用，项目唯一索引防止不同令牌或其他目录写入创建重复身份。注册发生唯一键冲突时，整个事务回滚，包括令牌消耗；返回明确的注册冲突错误，不返回凭据或把另一份注册的密钥当作本次成功结果。已经注册的项目继续使用签名重注册，响应不再次返回密钥。

新库与已有开发库升级均已包含该约束。真实 Spring/MyBatis 事务覆盖同令牌与不同令牌并发；MySQL 隔离表复验和开发库执行证据见 [项目身份整理记录](../../output/tasks/architecture-audit-20260905/registry-project-identity-notes.md)。

### 注册凭据与嵌入策略

`RegistrySecurityService` 统一维护凭据写入和主凭据选择；目录展示与轮换均按 `updated_at DESC, id DESC` 选择 ACTIVE 凭据。多个有效凭据仍可并存。

轮换只更新密钥标识、密钥和更新时间；写入时核对项目、ACTIVE 状态和读取时的完整密钥身份。并发停用或另一轮换已改变身份时，返回明确冲突，调用方重新加载后重试。身份比较区分大小写及字节长度，避免数据库默认排序规则或二进制补零掩盖变化。

管理端策略替换只写来源范围、Agent 范围、TTL 和显式指定的状态，省略状态时保留数据库当前值；空列表可清除对应范围。SDK 注册策略继续采用补丁语义，忽略空列表和非正 TTL。两条入口都不把读取过的整行凭据写回，避免恢复旧密钥或覆盖另一操作负责的字段。同一策略字段的并发替换仍按数据库实际写入顺序生效，未新增客户端修订协议。

### 首次接入异常恢复

Starter 将登记请求和收到凭据后的落盘放在同一客户端串行入口。收到有效响应但本地保存失败时，凭据由存储组件暂存在内存，下一次重试先完成保存，成功后才安装到签名配置；临时文件在写入失败时清理。未配置完整凭据的客户端在重试前重新读取本地凭据文件，允许使用另一实例已保存的结果。

若整个响应丢失，或进程在保存前退出，一次性令牌继续保持已消费状态。有权限的平台操作者通过既有项目凭据更新命令替换主凭据，把新的一对凭据配置到业务实例后重启；保留原项目、能力和策略，使用新签名完成重新登记。该路径会使旧主凭据失效，使用同一凭据的其他实例需要同步更新。它是明确的人工恢复路径，不允许重新兑换已消费令牌或从注册响应再次读取旧密钥。配置方式见 [Starter 恢复说明](../../reachai-spring-boot2-starter/README.md#recovering-interrupted-enrollment)。

### 能力接纳

1. SDK 的 `apply` 标记没有审批权。可信来源同步由服务端策略处理；开发诊断只生成候选，不能改变真实来源状态。
2. 同项目按数据库锁串行接收和决策。能力清单先校验和规范化；同一同步标识的不同内容拒绝。连续相同内容复用原快照，不重复创建待办。
3. 每个能力只保留当前候选作为待处理项。后续观察使旧候选失效，不能应用旧快照覆盖新来源；重复的已忽略变化保持安静。
4. 未变化自动结束；新的只读能力在完整定义校验通过后自动纳入目录；纯展示名称更新可自动接受。权限、开放范围、说明语义、副作用、输入输出契约与路由变化不能假定无风险。
5. 对未被使用能力的进一步自动接纳必须建立在完整引用与开放证据上。未知不能按零引用处理。先提供真实证据，不能用空数组制造确定性。
6. 自动接纳与人工接纳共用目录写入、冲突检查和审计。自动记录策略版本，人工记录可信登录身份；不保留另一条不受治理的批量应用主路径。
7. 来源契约和目录不一致、或来源已不再提供能力时，调用前阻断受影响能力并返回明确原因。忽略、回滚和刷新不能解除尚未解决的来源漂移。
8. 发布的 Workflow 和直接暴露能力的 MCP 发布固定当时的能力契约；执行前核对当前契约，避免目录人工更新后旧发布静默使用不兼容定义。重新校验与发布后采用新契约；没有契约指纹的旧发布不能跳过保护。
9. 待处理视图按能力展示当前例外和具体影响，默认隐藏无变化、自动完成与被替代的历史项。历史记录仍可查询，开发诊断单独保留。
10. 权限仍按项目隔离。入口位于能力目录，避免在导航中把正常使用组织为必须人工评审的流水线。
11. SDK 能力的扫描行与调用投影以服务端 `source_qualified_name` 绑定 `capability_source_state.qualified_name`。`source_location` 只描述来源位置，清空或改写它不能解除来源保护。旧扫描编辑、启停、重新扫描、纳入、推送和撤销，以及通用调用投影的修改入口，统一拒绝修改来源拥有的能力；SDK 同步和变化处理负责维护契约与启用状态。缺少来源绑定的旧 SDK 投影不能执行，需升级后可信同步。

## 部署与验证边界

1. 新库执行 [`sql/initV2.sql`](../../sql/initV2.sql)；已有开发/测试库按 [`升级脚本`](../../sql/upgrade-20260905-capability-change-governance.sql) 和 [`SQL 说明`](../../sql/README.md) 升级。本轮没有执行数据库变更。
2. 部署配套的 Capability、Runtime、Control 和管理端。SDK 能力重新进行可信同步，建立来源观察；旧快照默认作为诊断历史，不能反向证明当前业务来源有效。
3. 含能力调用的旧 Workflow，以及直接暴露能力的旧 MCP 发布，重新校验并发布以固定契约。迁移期间未确认的来源和未固定契约的旧发布会阻止相关调用。
4. 部署验收还需使用真实项目执行 SDK 同步、引用查询、接受变化、漂移拒绝、重新发布与业务调用。本轮浏览器验收没有覆盖这条真实跨服务链路。

来源一致性保护依赖业务系统上报的声明。它能发现声明契约的漂移，不能证明未上报的实现、业务语义或业务数据没有变化，也不能通过恢复目录回退业务代码。
