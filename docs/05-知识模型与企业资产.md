# 知识、模型与企业资产

## 定位

ReachAI 的知识与资产体系分为两条主线：

- Knowledge / Retrieval：知识库、文件、Chunk、向量检索、RAG、业务索引和检索评测。
- Capability Catalog：业务能力、Tool、项目 API 管理、能力快照、字段级 diff、评审和发布治理。

两者协作但不混同。知识检索由 `reachai-knowledge-service` 承接；能力资产由 `reachai-capability-service` 承接；公共管理入口由 `reachai-control-service` 暴露。

## 五服务关系

| 服务 | 与知识和资产的关系 |
| --- | --- |
| `reachai-control-service` | 提供管理端 `/api/**` BFF 和公开入口，聚合 Runtime、Capability、Knowledge、Model 的状态和公共操作。 |
| `reachai-runtime-service` | 在 Agent / Workflow 执行时消费 Capability 和 Knowledge，生成 Trace、RunOps 和调试数据。 |
| `reachai-capability-service` | 管理能力资产、SDK 注册、项目 API 管理、扫描项目目录、能力快照和变更评审。 |
| `reachai-knowledge-service` | 管理知识库、文件、Chunk、RAG、向量检索、业务索引和扫描器实现。 |
| `reachai-model-service` | 提供 Chat、Embedding、Rerank 和模型实例能力，供 Knowledge 和 Runtime 调用。 |

第一阶段保持同一个 MySQL 库，不拆库，但新增实现必须尊重 owning service 边界。

## 知识模型

核心实体包括：

| 实体 | 说明 |
| --- | --- |
| `knowledge_base` | 知识库定义、可见性、Chunk 策略和业务配置。 |
| `knowledge_file_info` | 文件元数据、解析状态、入库状态和归属知识库。 |
| `knowledge_chunk` | 文本 Chunk、向量写入状态、来源文件和检索元数据。 |
| `knowledge_business_index` | 面向业务对象的语义索引定义。 |
| `knowledge_business_index_record` | 业务对象记录及其可检索内容。 |
| `knowledge_user_file_permission` | 文件级权限过滤的基础数据（仅 `access_mode=FILE_GRANTS` 的知识库使用）。 |
| `knowledge_hit_log` | 检索命中记录：问题、分数、命中文件；`source` 区分真实对话（RUNTIME）和管理端检索测试（CONSOLE），不存回答。 |

这些表当前仍位于统一 SQL 基线中，入口是 `sql/initV2.sql`。标签（`knowledge_tag`）和问题映射（`knowledge_question`）在 2026-10-18 知识模块整理中删除：检索从未使用它们。

## 知识库怎么被 Agent 用上

2026-10-18 起（[知识模块整理方案](plans/知识模块整理方案.md)）：

- **谁能检索**：知识库 `access_mode` 默认 `ALL_CALLERS`，调用使用该库的 Agent 的所有用户都能查到启用段落；`FILE_GRANTS` 才按 `knowledge_user_file_permission` 逐文件过滤。管理端「检索测试」和终端用户看到的结果因此一致（`FILE_GRANTS` 时页面会提示差异）。
- **检索设置**：Workflow 知识节点没填的返回条数、相似度下限、检索方式、重排一律取知识库设置，再没有才用全局默认。「直接返回」已删除（Runtime 不支持）。
- **接入 Agent**：知识库详情「接入 Agent」调用 Runtime `POST /api/agents/{agentId}/knowledge-qa`，在 Agent 所属项目生成并发布模板 Workflow `kb-qa-<项目>-<知识库>`（用户问题 → 知识检索 `evidencePolicy=REQUIRED` → 模型按资料回答并注明出处 / 无依据时固定回复「资料里没有」），再作为 Workflow-as-Tool 加入 Agent 并发布配置。该 Workflow 之后可在 Studio 里正常修改。`GET /api/workflows/knowledge-usage` 列出用到某知识库的 Workflow 和 Agent。
- **切分**：Markdown 按标题切成段落（`sectionPath` 为标题链），Word（Docling）同一标题下的连续段落合并后再按长度切。改切分设置后对已有文件「重新解析」生效。
- **管理端**：知识库详情只有 文件（页内上传）/ 检索测试 / 命中分析 / 设置 四个页签；旧「文件入库」「实验室 → 知识检索测试」链接跳到对应页签。业务索引不在「知识」导航里，从「项目接入 → 项目详情」进入，目前 Agent 还不能直接检索业务索引。

## 能力资产模型

Capability Catalog 关注可执行或可治理的企业能力。典型资产包括：

- SDK 主动注册的项目、实例、能力和参数。
- 扫描项目产生的接口目录、Tool 定义和调用图谱。
- 能力快照、字段级 diff、评审记录、apply/ignore 结果。
- Runtime 可调用的 Tool / Capability 元数据和治理策略。

历史扫描器实现仍由 Knowledge / Retrieval 服务提供底层 OpenAPI 和 Controller 解析能力，但扫描项目目录、资产沉淀和能力治理归 `reachai-capability-service`。

## 模型中心

`reachai-model-service` 只维护两类持久对象：

- `model_template`：Provider/协议模板和参数 Schema，不保存用户密钥。
- `model_instance`：稳定 `modelInstanceId`、连接配置、加密凭据引用、测试与归档状态。

公共路径为 `/model/templates`、`/model/instances`、`/model/chat`、`/model/chat/stream/events`、`/model/embedding` 和 `/model/rerank`。已退役的 `/model/openai-proxy` 不再是接入方式。Knowledge 和 Runtime 通过明确的 Model client 使用实例，不自行保存第二套 Provider 密钥。

## 数据事实与检索投影

- Knowledge 文本、向量和 Business Index 都是检索资产，不自动成为授权事实。
- 个人长期记忆的 canonical owner 在 Control，`knowledge_personal_memory_index` 只是可重建投影；命中后仍需回读 canonical item。
- 订单、客户等业务对象以原业务系统为事实源。Business Index 命中只提供带版本引用，Runtime 必须在当前可信业务身份下调用 resolver 重新鉴权和回读。
- `KNOWLEDGE_RETRIEVAL` 的 `NO_EVIDENCE` 是成功业务分支；`evidencePolicy=REQUIRED` 时必须直接给出无证据回答，不能继续让 LLM 凭空补全。

## 约束

- 不再把 Knowledge / Retrieval 描述为旧的技能服务。
- 能力资产 API 不应绕过 `reachai-capability-service` 写入对方表。
- RAG、Embedding、Rerank、模型调用应通过 `reachai-model-service` 或明确的服务间客户端完成。
- 前端使用 `/api/**`、`/ai/**`、`/model/**` 三类入口，不重新依赖旧大后端。
