# 运行中心整理方案

> 2026-10-17 起草。依据：[平台定位与架构总览](../01-平台定位与架构总览.md)、[人员角色与权限重设计方案](人员角色与权限重设计方案.md)。目标是让运营人员在一个地方看清 Agent 跑得怎么样：从一次出错的对话，一路查到出错的节点，再把它变成评测用例防止复发。

## 1. 现状（dev 3a322b94 核对）

| # | 问题 | 证据 | 影响 |
| --- | --- | --- | --- |
| P1 | 运行记录、自动化、评测分在三处；评测没有菜单入口，只能从 Agent 列表的「更多」进入，而且只能看单个 Agent | `router/index.ts` 的 `/runops`、`/automations`、`/agent/:id/evals`；`sidebarMenu.ts` 运行中心只有两个子项 | 运营人员不知道有评测；看不到全平台评测结论 |
| P2 | 没有「对话」视角。完整对话账本 `runtime_conversation_session/_event` 已按轮次记录 traceId，但管理端没有任何页面能看；运行记录不能按会话或业务用户查 | `RuntimeRunOpsQueryService.findRecentRuns` 的 keyword 不含 `session_id`、`external_user_id`；运行详情没有「所属对话」 | 用户说「助手刚才答错了」，运营只能猜时间去翻运行记录 |
| P3 | 自动化执行器和评测执行器默认关闭；自动化页有「引擎关闭」提示，评测页没有 | `reachai.runtime.automation.enabled`、`reachai.runtime.eval.worker-enabled` 默认 false；评测页只在 QUEUED 时提示「请确认 worker 已开启」 | 实验一直排队，看起来像坏了；线上自动化也没有真正运行 |
| P4 | 运行详情不能直接沉淀为评测用例；方向只有评测页里手填 Trace ID | `AgentEval.vue`「从 RunOps Trace 反哺数据集」 | 定位完问题后要复制 ID、换页面、再选数据集 |
| P5 | 旧版评测 v1 仍在：Runtime 控制器、服务、4 张表和 Control 代理接口，前端已不用 | `RuntimeAgentEvalController`、`ControlRuntimePublicController` 的 `/api/runtime/evals/datasets` 等、`runtime_agent_eval_*` | 两套评测模型，维护和权限都要算两遍 |

运行详情本身已经有「定位失败点」和节点检查器（`RunOpsInvestigationWorkbench.vue`），这部分保留，不重做。

## 2. 目标形态

2026-10-19 用户确认将自动化拆为独立菜单 `/automations`，按 `automation:read` 显示；2026-10-20 恢复功能分组后，自动化中心与运行中心并列放在「运行与治理」组。旧地址 `/runops/automations` 保留重定向并携带查询参数和锚点。自动化页不再显示运行中心页签，执行历史仍可链接到运行详情。以下分批和验收记录保留原实施过程。

运行中心是「运行与治理」组下的一个菜单项，进去后是三个页签，按权限显示：

| 页签 | 回答的问题 | 权限 |
| --- | --- | --- |
| 对话 | 某个用户、某个 Agent 的对话说了什么，哪一轮出错 | `runops:read` |
| 运行记录 | 现有运行列表和诊断（失败聚类、版本健康） | `runops:read` |
| 评测 | 全部 Agent 的数据集和实验，发布前对比新旧配置 | `agent:evaluate` |

排查主线：对话 → 出错的那一轮 → 运行详情（已有失败点定位）→ 「加入评测集」→ 改配置后在评测页对比实验 → 发布。

相关页面互相跳转都带上筛选条件：对话里的一轮打开对应运行；运行详情显示所属对话；独立自动化页面的每次执行链接到运行；评测逐项结果链接到运行。

## 3. 分批

### C1 入口归一（管理端）
- 新增运行中心外壳页，四个页签对应子路由：`/runops/conversations`、`/runops`（运行记录，保持现有地址）、`/runops/automations`、`/runops/evals`；评测工作台移到 `/runops/evals/:agentId`。
- 旧地址 `/automations`、`/agent/:id/evals` 重定向到新地址，带上原查询参数。
- 侧边栏「运行中心」改为单个菜单项；概览页的角色快捷入口给运营人员加上运行中心。
- 新的评测总览：跨 Agent 列出数据集和最近实验（结论、分数差、状态），按 Agent 和项目筛选，点进去是现有评测工作台。
- 对话页签在 C2 前先不显示。不改后端和表结构。

### C2 对话视角（Runtime + Control + 管理端）
- 对话正文取 Control 自有的嵌入式对话事件（`control_embed_session` / `control_embed_chat_event`），因为终端用户只通过嵌入式对话使用 Agent，而 Runtime 的会话账本只在开启会话记忆时才写；每轮的运行状态从 Runtime 根运行按会话 ID 读取。各服务只读自己的表。
- Control 新增 `GET /api/runops/conversations` 和 `GET /api/runops/conversations/{sessionId}`，需要 `runops:read`，按项目范围过滤（与运行记录相同的规则）。
- 「对话」页签：左侧会话列表，右侧聊天记录式展示，失败或未完成的轮次标红，每轮「查看运行」打开运行详情。
- 运行记录：关键词也匹配会话 ID 和业务用户 ID；运行详情的「运行上下文」显示所属对话并可跳转。
- Agent 编辑页的「嵌入」分区保留嵌入会话审计（页面、来源等嵌入信息），会话行加「在运行中心查看对话」。
- 不改表结构（复用现有索引；如果实测发现缺索引，会单独请你确认 SQL）。

### C3 闭环与执行器状态
- 运行详情和对话轮次加「加入评测集」：选择该 Agent 的数据集（或新建），复用现有 from-trace 接口，需要 `agent:evaluate`。
- Runtime 报告评测执行器是否开启（自动化已有 `/api/automations/readiness`）；评测页签在关闭时顶部明确提示「评测执行器未开启，实验不会运行」，并禁用「开始实验」。
- 宝塔线上开启两个执行器，并发设为 1（服务器内存紧张）；这是 Runtime 启动参数调整，不改库，由部署线程执行。

### C4 清理与验收
- 删除评测 v1：Runtime 控制器、服务、实体、Mapper，Control 代理接口和权限规则；`initV2.sql` 去掉 `runtime_agent_eval_*`，对应升级现合并至 `upgrade-20261019-consolidated.sql` 段落 09（同时给 `runtime_run` 加 `session_id` 索引），同步 `service-table-ownership.md`。线上执行这份删表 SQL 前会单独请你确认，并先备份 reach_ai。
- 更新 `docs/01` 和运行中心相关文档。
- 线上验收：在芋道里让 ERP 助手答一个会失败的问题 → 运行中心「对话」按业务用户找到这次会话 → 打开失败轮次的运行，定位到出错节点 → 加入评测集 → 发起一次对比实验并跑完；另建一个每天执行的 ERP 助手自动化，手动触发一次并看到运行记录。

## 4. 影响与风险

- 线上库：C1–C3 预计不改表结构；C4 删除 4 张已不使用的旧评测表，需要你确认。
- 线上配置：C3 开启自动化和评测执行器，会多占一些 Runtime 内存和数据库连接；并发设为 1，部署后观察内存。
- 兼容：旧地址都做重定向；评测 v1 接口删除后不再可用（前端早已不用）。
- 每批一个 PR 合并到 dev，经「部署项目到宝塔」线程上线。

### 线上验收（2026-10-17，芋道 ERP 助手）

主流程全部通过：对话页按业务用户找到会话 → 失败轮标红 → 运行详情定位到「智能体调度」节点 → 加入评测集「ERP 助手回归」→ v4 对 v5 对比实验 4/4 通过 → 自动化「ERP 助手每日库存预警」（每天 09:00）手动触发成功并链接到运行。验收发现的问题随后修复：

- 自动化运行历史按浏览器时区显示时间，改为按自动化自己的时区显示。
- 失败原因脱敏后只显示 `[omitted]`，改为按错误码给出中文说明（例如模型服务请求失败）。
- 长时间空闲后第一次模型调用偶发 Connection reset，model-service 在未收到任何响应时重试一次（超时不重试）。
- 「加入评测集」可直接新建数据集（只填名称），当前运行就是第一个用例；Agent 自动化的输入改为「问题」输入框。
- Agent 运行的 Token 一直记为 0：各轮用量只在 `supervisor.modelRounds` 里而汇总时被跳过，改为记录各轮之和。
- 芋道传给嵌入令牌的 `userName` 是登录名，要显示昵称需要改芋道侧补丁。
