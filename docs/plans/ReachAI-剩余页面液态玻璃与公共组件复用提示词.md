# ReachAI 剩余页面液态玻璃改造与公共组件复用提示词

> 续做提示词，更新于 2026-10-22。可把本文全文连同用户提供的两张参考图交给拥有仓库访问权限的编程模型直接执行。本文记录当前方向和代码入口，执行时仍须核对实际工作树。

## 任务

你现在接手 ReachAI 管理端剩余页面的液态玻璃改造。主页面已基本完成，本轮重点是尚未完整适配的子页面、二级/三级页面、详情页、标签页、弹窗、抽屉、局部侧边栏及其内部控件和状态。请沿用现有设计，补齐遗漏，并将可复用组件、交互外观和样式收敛到同一套公共实现。

这是实施任务：先检查代码和页面，简要说明批次安排，然后直接修改、验证、持续推进。不要只输出建议、设计方案或几个样板页后结束，也不要逐页要求用户重复确认已授权的常规 UI 修改。

目标是让剩余页面具备统一、精细、紧凑的液态玻璃体验，同时改善信息层级和工作效率。既要看起来一致，也要保证搜索、筛选、翻页、表单、权限和业务操作继续正常。

**最高优先级：不要丢功能。优先顺序是：功能完整性与数据正确性 > 文字可读性与操作可达性 > 视觉一致性 > 装饰效果。**

- 这是现有产品的界面迁移，不是重新实现一个功能简化版。默认保留每个字段、操作、条件分支、业务提示和完整流程；可以调整布局与视觉层级，不能擅自删减业务内容。
- 不能以“不常用”“影响美观”“暂时难以适配”为由，删除、隐藏或永久禁用已有功能，也不能把高级配置、错误详情、危险操作确认或权限限制一起删掉。
- 禁止用静态数据、假成功提示、空事件或只能展示的组件替代真实操作。真实接口与持久化行为必须延续；模拟只能作为明确标注的验证手段。
- 某个复杂控件暂时不适合公共包装时，保留原控件的完整行为，用共享 token / 材质适配外观，并记录剩余差异。不要强行替换后损失能力。
- 改造后凡是原来能找到、能执行、能保存、能恢复、能查看结果的功能，都要仍然可达、可用。截图更好看不能抵消功能回归。

## 二、必须延续的设计方向

### 两张截图表达的目标

- 项目管理列表截图是已有风格的参考：壁纸、侧栏、选中胶囊、筛选区、列表阅读面和分页已经形成统一语言。延续当前已完成的方向，避免重做主页面或另造一套风格。
- “接入项目”弹窗截图是本轮要深入检查的典型：外面的列表已经适配，但里面的标签页、表单、选择器、提示区和底部操作仍需逐项核对。外壳用了 `AppDialog`，不等于内部和后续流程已全部完成。
- 弹窗不是越透明越好。保留现有高浓度阅读底，通过统一的边缘、高光、厚度、控件与层级体现玻璃质感；不能让底层列表文字透进表单。可读性优先于透背景。
- 截图用于说明视觉问题，不是路由、菜单、命名和业务语义的权威来源；这些以当前仓库为准。不要因为截图里有旧入口而恢复退役功能。

用户喜欢清透、具有曲面厚度和边缘折射的液态玻璃，尤其关注按钮、选择器、展开菜单、分段导航和分页器。用户也明确不喜欢：

- 只增加透明度、模糊和圆角，却没有液态层次。
- 深色壁纸上出现大面积灰白、灰紫色块。
- 下拉选项透出底层业务文字，或者弹窗过透导致看不清。
- 卡片外再套一块大白玻璃框，形成多层厚重容器。
- 标题、英文眉题、辅助标签、统计条反复表达相同信息。
- 巨大的统计面板挤占首屏，卡片名称被标签挤得只剩半行。
- 加载时整片列表突然变成白色遮罩。

遵守这些原则：

1. **先改善层级，再调整材质。** 每页先判断主要任务、主要操作和最重要的信息。名称与业务用途优先；标识、版本、来源等信息降低视觉分量。不要通过过小字体换取紧凑。
2. **导航和控件有液态感，内容有稳定阅读底。** 复用现有曲面折射、非均匀亮边、底缘焦散和厚度阴影。文字与图标不进入光学滤镜。表格、表单、日志、代码和长正文保持可读。
3. **减少重复容器。** 有独立阅读卡片的目录，可使用公共 collection 布局；需要整片阅读面的表格或表单，保留 panel 布局。不能把所有页面机械改成同一种网格或极透明外壳。
4. **页头克制。** 主操作清晰突出，次操作收敛。标签使用公共位置；可合并纯装饰性的重复表达，但原有业务信息、入口和说明必须仍然可见或有明确可达位置。少量计数用行内摘要，有必要才使用独立统计面板。
5. **内容与状态清晰。** 长名称合理换行或提供完整内容查看入口；不要让包标识、每一个字段都变成彩色胶囊。状态色表达成功、警告、危险，不随品牌任意改义。
6. **保留工作台密度。** 筛选和结果紧密衔接，结果区合理利用高度，分页可见，内容按既有规则滚动。避免为几条数据铺巨大空白区域，也避免固定高度裁掉卡片或操作区。

## 三、公共组件与样式必须复用

统一导入入口：

```ts
import {
  LiquidGlassPage,
  LiquidGlassTable,
  LiquidGlassCard,
  LiquidGlassEmptyState,
  LiquidGlassNotice,
  LiquidGlassFilterBar,
  LiquidGlassButton,
  LiquidGlassInput,
  LiquidGlassSelect,
  LiquidGlassPagination,
  LiquidGlassViewToggle,
  LiquidGlassNav,
  LiquidGlassTabs,
  LiquidGlassDropdown,
  PageHeaderTags,
} from '@/components/common/liquid-glass'
```

| 场景 | 优先复用 |
| --- | --- |
| 工作台列表页与高度边界 | `LiquidGlassPage` |
| 筛选、结果、加载、空态和分页 | `LiquidGlassTable`，保留原生业务表格列与业务状态 |
| 独立卡片目录 | `LiquidGlassTable body-layout="cards" presentation="collection"` + `LiquidGlassCard` |
| 单行搜索、筛选和主要操作 | `LiquidGlassInput / Select / Button / FilterBar` |
| 前后翻页、页码与每页条数 | `LiquidGlassPagination`，或 Table 的默认分页 |
| 页面功能导航 | `LiquidGlassNav`，内部保留原生按钮或 RouterLink |
| 原生标签页 | `LiquidGlassTabs` + `el-tab-pane`，保留 `before-leave` |
| 整理、更多操作等菜单 | `LiquidGlassDropdown` + `el-dropdown-menu/item` |
| 页头与辅助标签 | `PageHeader`，使用既有 `tags / meta / actions` 插槽；标签位置由 `PageHeaderTags` 管理 |
| 少量页头计数 | `MetricStrip presentation="inline" source="wallpaper"`，从其原有 common 路径导入 |
| 空结果与引导 | `LiquidGlassEmptyState`；项目范围提示继续使用 `ProjectScopeState` |
| 普通对话框与抽屉 | `AppDialog / AppDrawer`，统一外壳、阅读面、滚动和基础交互 |
| 已有组合式弹窗与分步向导 | 先检查 `GlassDialog / WizardDialog`；它们基于现有 `AppDialog` 组合，不再平行新建另一套玻璃弹窗体系 |
| 复杂表单、多行输入、编辑器和专用控件 | 保留原有成熟控件与既有阅读配方，按需组合公共单行控件；不能为了组件名字统一而强换 |
| 说明、警告与错误提示 | `LiquidGlassNotice`；保留原有提示内容、出现条件、恢复和重试操作 |

接入前阅读源码核对属性、事件、插槽和 ref 能力，不能臆造组件 API。

封装规则：

- 先复用已有组件；存在真实缺口时，扩展现有公共组件或共享 token，再接入实际页面。
- 通用布局和材料放在 common / styles；有业务含义的内容组件放在所属模块，组合公共组件。不要把业务数据请求、权限判断或项目范围管理塞进通用外观组件。
- 提炼重复模式时明确真实使用场景。不要建立大量仅包一层、职责重复、无人使用的组件；不要为了统一外观制造巨型配置驱动页面。
- 页面样式主要保留布局、尺寸、业务内容差异。玻璃底、模糊、高光、圆角、边框、主题颜色和阴影由公共实现维护。
- 新增公共能力应有保守默认值，既有消费者保持原有表现。改公共层后，回归一个原使用者和一个新接入者。
- 统一的是组件实现和样式来源，不是强迫所有场景长成同一种布局。尺寸、密度、材质来源和必要变体通过清晰的 props / slots / token 表达，避免每个页面再写一套同名玻璃样式。
- 检查已有组件的属性、事件、动态/作用域插槽、`v-model`、透传属性和公开 ref 方法。包装后的 `focus / blur / validate / reset` 等能力按原组件实际用途保持；不要靠类型断言掩盖缺失能力。
- 移除本批页面已被公共层接替的旧样式，避免并存两套配方。不顺手清理无关 WIP。
- 不用全局替换或增加大量 `!important` 掩盖局部问题，也不能通过删除检查或放宽断言让验证变绿。

## 四、主题、浮层、加载与交互的具体要求

### 材质来源与主题

- 工作台壁纸上的独立控件使用 `source="wallpaper"`。Table 内的公共控件可继承来源；默认 backdrop 适合局部阅读面和弹窗。
- 使用现有 `glass-workspace-adaptive` 和语义 token 适配深色壁纸。科技紫、星云紫、珊瑚玫、深海蓝不能沿用一大片白色阅读底。
- 裸露在壁纸上的文字使用 `--text-on-wallpaper*`；面板内文字使用对应阅读面前景。品牌壁纸明暗和用户选择的明暗模式是两回事。
- 来源与局部配色只作用于需要的表面，不把整页、标签页全部内容或兄弟弹窗染成同一套颜色。Teleport 浮层显式保留正确来源与阅读色。
- 使用现有七套主题和壁纸资源，不硬编码页面级品牌判断，不新建第二套主题系统，不擅自更换壁纸或清除用户偏好。
- 保留减少透明度、减少动态效果、关闭折射、无滤镜支持、强制颜色等回退。不要在每张卡片、每一行或每个节点上生成光学贴图。

### 下拉、分页、加载

- 下拉和操作菜单复用公共水滴轮廓及表面，保留轻微不规则的肩部与连体感；选项文字、命中区域和键盘导航保持规则清晰。不要重新加原生尖三角或做成普通白色矩形。
- 分页复用连续玻璃操作坞、选中块和条数选择器。保持原有本地/服务端分页边界，不把全部数据拉回前端冒充分页。
- 服务端分页优先绑定单一 `change(page, pageSize)`；避免同时监听多种事件重复查询。变更条数回到第一页，父级主动更新模型不反向触发请求。
- `DataTableShell / LiquidGlassTable` 和 `LiquidGlassCard` 已提供 `glass-loading-surface`。加载保留原阅读底和内容，以薄雾和小型提示表达等待；不得重新铺近白色大遮罩。完成、失败、重试都应正确结束或恢复加载状态。
- 固定操作列浮起时必须遮住下层滚动文字。不要为追求透明把列背景清空，也不要改回突兀白底；复用已有主题混合底与窄屏规则。

### 弹窗、抽屉与局部侧边栏

- 同时检查标题区、说明区、标签页、分组、表单控件、校验消息、代码区和 footer。统一外壳只是第一步，不能留下“外面玻璃、里面一整套旧风格”。
- `AppDialog / AppDrawer` 仍是基础；需要组合头部或步骤布局时复用已有 `GlassDialog / WizardDialog`。公共材质统一维护在现有样式层，业务页面只负责内容与布局。
- 沿用当前 `--surface-glass-overlay` 等共享阅读 token，保留高浓度表面。不能用降低整个弹窗 `opacity` 来制造透明效果，否则文字与控件也会变淡。
- 多选、远程搜索、级联/树选择、日期、上传、密码、只读字段、多行文本和编辑器分别核对原能力。公共组件不支持时先补足兼容或保留原生控件，不做有损替换。
- `Teleport` 到 body 的选择器、日期面板、Popover、Tooltip、右键菜单和确认框也在范围内。核对主题继承、`popper-class`、层级、裁切、定位和点击区域，不能只改触发按钮。
- 保留 ESC、遮罩点击、右上角关闭、取消、提交中禁止关闭、`before-close`、未保存确认、焦点约束与关闭后焦点返回等原有行为。保留多层弹窗的滚动锁和正确关闭顺序。
- 内容较长时正文可滚动，操作区可达；窄屏、长错误信息、校验展开后都不能裁掉字段与按钮。装饰层不得遮挡点击、文本选取、拖拽或编辑器输入。
- 区分页面局部侧边栏和全局主菜单。侧栏展开/收起、树节点状态、拖动分隔条和宽度行为按原功能保留；如果隐藏可视滚动条，仍须支持滚轮和键盘滚动。

### 原生能力与业务行为

- 保留原生 `v-model`、插槽、禁用/加载状态、清除、焦点、键盘、校验、IME 输入和 ref 能力。
- 筛选表单统一通过 `query` 提交，避免再给同一个输入额外绑定重复请求的 Enter 事件。保留原页面已确认的即时筛选或显式提交方式。
- 保留标签页未保存离开确认、路由 query/hash、项目切换、权限按钮、服务端状态与错误反馈。
- 卡片中有按钮时，避免点击或键盘事件冒泡造成两次打开；可点击区域应有真实键盘入口和清晰焦点。
- 不因样式迁移改变字段含义、治理状态、默认版本、发布关系、调用能力或权限。不要把界面里存在的数据声明成已验证的运行结果。

## 五、从实际代码找出剩余页面，分批完成

先建立“父页面 → 入口/按钮 → 子页或弹层 → 内部标签页/步骤 → 状态”的覆盖清单。不能只扫侧栏和一级路由；没有独立路由、需要操作后才出现、依权限或数据条件显示的界面同样属于范围。先递归检查真实路由及页面内部入口，区分：

1. 已接入最新公共组件并需要保留的页面。
2. 仅有旧 token / 旧玻璃覆盖，尚未接入本次公共组件或层级仍明显不好的页面。
3. 已迁移页面里的遗漏状态、子页、详情、弹窗、抽屉、空态和加载态。
4. 特殊工作区，需要定向接入公共材料而不能机械套列表壳。

在既有迁移矩阵中补充本轮条目或子条目，至少记录：所属路由、具体打开路径、组件文件、需要复用的公共能力、功能核对项、视觉状态、功能状态、证据和阻塞。页面、内部弹层和功能验证分别记账；历史的“已迁移”不能自动覆盖新发现的遗漏。

### 不丢功能的工作方法

每组改动前先从真实模板、事件处理、composable、接口调用和现有测试建立功能基线，并在能运行的浏览器中走通代表路径。每个受影响入口至少覆盖以下适用项：

| 核对面 | 改造前后必须保持 |
| --- | --- |
| 入口与权限 | 原路由、参数、按钮、条件显示、只读/禁用与权限边界，直接访问和返回路径 |
| 字段与表单 | 字段、默认值、必填/校验、联动、隐藏分支、上传、动态行、只读与敏感信息显隐 |
| 事件与状态 | 原 `v-model`、事件参数、插槽、ref、步骤/标签切换、未保存确认、取消与重开后的清理/恢复规则 |
| 数据操作 | 原接口、请求参数、次数、保存/发布/删除语义、真实返回值、刷新后的持久化结果与失败反馈 |
| 查询与结果 | 原搜索触发方式、过滤/排序、服务端分页、选择与批量操作、导入导出、详情和复制/下载 |
| 特殊工作区 | 画布拖拽、连线、缩放、快捷键、配置编辑、预览/应用、调试、发布与回放等实际已有能力 |
| 状态与可达性 | 加载、空态、报错、重试、提交中、防重复提交、键盘焦点、长内容与滚动 |

对照基线记录“原行为 → 本轮结果 → 验证证据”。新发现的原有缺陷与本轮回归分开记录，不能因原来有缺陷就跳过核对，也不要顺手扩展成无关业务重构。复用公共层后，除了当前页面，还要回归原有消费者，尤其是已有主页面和复杂弹层。

涉及服务端写入时，在合适的本地/测试数据上验证成功、失败和重开/刷新结果；破坏性操作需要按仓库规则处理。没有可用后端或必要权限时，先完成可验证部分，保留对应的未验证状态。模拟响应、静态预览或按钮可点击都不能作为真实保存成功的证据。

### 代码检查

在 `ai-admin-front` 目录运行适用命令，以当前 `package.json` 为准：

```text
npm run build
npm run test:liquid-glass
npm run check:glass-theme
npm run check:glass-components
npm run check:dark-theme-compatibility
npm run check:page-rhythm
npm run check:page-header-family
npm run check:overlay-migration
```

按本批页面补充相应模块测试与 UI 契约，不必无差别重跑所有测试。对原生事件转交、未保存离开确认、分页重复请求、键盘打开等真实行为变更补必要回归；不为纯可逆的间距调整堆砌镜像实现的测试。最后运行 `git diff --check`。

起始就有失败时，先保存原结果并定位与本批差异的关系。不得把历史通过记录当作当前通过，也不得通过削弱校验绕过失败；明确已修复问题、既有问题和实际未完成检查。

### 浏览器与视觉检查

- 先确认实际本地端口、进程和登录状态；不要盲目启停用户服务或绕过正常认证。没有后端时可用真实组件的独立模拟预览验证 UI，但必须标注为模拟预览。
- 至少检查翡翠绿亮色，以及科技紫、星云紫、珊瑚玫等深色壁纸；同时检查用户的明暗模式。公共材质变化应覆盖七套品牌的相关组合。
- 检查正常结果、空结果、首次/再次加载、失败重试、禁用、选中、焦点、菜单展开、分页和长文本。
- 对照本批功能基线逐项操作：表单提交与校验、切换和返回、保存后重开/刷新、取消与关闭、复制/下载等。检查一次操作只产生预期次数的请求，最终数据和页面状态与原契约一致。
- 对每类弹层至少打开其内部选择器/菜单并操作，检查 Teleport 层级、关闭顺序、焦点与滚动。不能只交付弹窗刚打开时的一张截图。
- 检查宽屏、常用笔记本窗口及 390/320 像素窄屏；关注横向溢出、固定列、卡片裁切、滚动区、底部分页和弹层位置。
- 检查减少透明度、减少动态效果、强制颜色等回退，确认文字仍可读、焦点可见。
- 截图后真正查看并自我评审：首屏是否更有主次？是否仍有大白框或重复玻璃？深色是否发灰？字号是否为了紧凑而过小？只有代码检查通过不算视觉完成。
- 热更新不稳定时刷新或使用新的独立页面验证最后源码，并检查最终控制台。不要用旧截图或手工注入的试验样式冒充最终效果。

### 完成标准

剩余活跃页面及其内部子页、弹层、分支和状态均已盘点；可复用模式落入公共组件或样式并被实际接入；页面重复配方被收敛；主题、信息层级和功能基线完成本批验证。确实无需改动的页面应说明原因并记录核对证据，不为凑迁移数量重写。

每个迁移入口都应能回答：原来的功能在哪里，哪些真实操作已回归，哪些仍缺环境或证据。不能只交组件替换数量和截图，不交功能核对结果；发现回归应先修复再继续推广。存在未验证入口时，交付中明确列出，不能宣称全站改造与功能验收已经完成。跨会话继续时依照更新后的矩阵和实施记录续做，不能把未完成项静默省略。

交付时简洁说明：本批改了哪些页面、复用了或扩展了哪些公共能力、有什么可见改善、实际运行的检查与截图、真实联调和模拟预览的边界、剩余事项、提交/部署状态。保留与任务无关的 WIP，不把模拟数据、构建成功或旧部署记录写成当前生产验收通过。

现在开始：先检查工作树、公共指南和真实路由，给出简短的剩余界面覆盖清单与功能基线，从项目接入完整流程和公共层缺口开始实施，验证后持续推进全部剩余范围。始终记住：能复用的尽量使用同一个实现，任何视觉改造都不能以丢功能为代价。
