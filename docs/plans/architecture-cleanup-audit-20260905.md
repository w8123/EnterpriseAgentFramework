## 4. 行为与契约问题

### R1：能力来源和目录写入需要统一归属

当前治理主线由 `CapabilityRegistryService`、`CapabilityChangeLifecycle`、`CapabilityChangePolicy` 处理来源观察、候选、接纳、审计和契约保护。但扫描目录仍有另一套写入路径：

- [扫描目录 Controller](../../reachai-capability-service/src/main/java/com/enterprise/ai/capability/catalog/scan/CapabilityScanProjectCatalogController.java) 暴露编辑、推送、提升和取消关联入口。
- [updateTool](../../reachai-capability-service/src/main/java/com/enterprise/ai/capability/catalog/scan/CapabilityScanProjectCatalogService.java) 接收并覆盖 `sourceLocation`、路由和参数等字段，未把 SDK 来源能力分流到变更治理。
- [pushToolToGlobal](../../reachai-capability-service/src/main/java/com/enterprise/ai/capability/catalog/scan/CapabilityScanProjectCatalogService.java) 直接更新 `ToolDefinitionMapper`；[投影组装](../../reachai-capability-service/src/main/java/com/enterprise/ai/capability/catalog/scan/CapabilityScanProjectCatalogService.java) 同时重写来源、限定名和副作用字段。
- [来源保护](../../reachai-capability-service/src/main/java/com/enterprise/ai/capability/internal/CapabilitySourceContractGuard.java) 以可编辑的 `sourceLocation` 是否以 `sdk:` 开头决定是否查询来源状态。
- Control 的 [扫描目录代理](../../reachai-control-service/src/main/java/com/enterprise/ai/control/compat/CapabilityCompatibilityProxyController.java) 仍转发这些已受控制台认证保护的路径。

本地复现先建立来源契约一致的 SDK 能力。经真实 `updateTool` 和 `pushToolToGlobal` 修改路由后，真实策略哈希与来源保护得到 `CONTRACT_DRIFT`；再通过同一编辑请求清空 `sourceLocation`，保护得到 `READY`，且完全没有查询来源状态。复现还观察到限定名被重新派生。

证据：[复现程序](../../output/tasks/architecture-audit-20260905/CapabilityLegacyMutationAudit.java)、[运行结果](../../output/tasks/architecture-audit-20260905/CapabilityLegacyMutationAudit.result.json)。数据库 Mapper 使用替身，没有写入真实数据或发起 HTTP 调用。该复现验证来源保护缺口；已发布调用的 `expectedContractHash` 校验仍是独立保护层。

目标设计：来源身份由服务端稳定绑定决定；SDK 声明中的调用契约只能通过统一接纳流程改变。扫描编辑入口必须按来源权威明确允许字段，目录投影的写入与删除共用 owning service 的业务入口。展示信息覆盖应有明确字段范围，不能顺带改变来源身份。

### R2：发布版本需要携带完整执行上下文

[发布校验](../../reachai-runtime-service/src/main/java/com/enterprise/ai/runtime/workflow/RuntimeWorkflowReleaseValidationService.java) 允许模型节点使用 Workflow 默认模型；[发布快照](../../reachai-runtime-service/src/main/java/com/enterprise/ai/runtime/workflow/RuntimeWorkflowVersionService.java) 保存该默认值。

但执行入口的处理不同：

| 入口 | 当前源码行为 |
| --- | --- |
| Agent Supervisor | 从发布快照读取默认模型，并在执行前设置 `workflowDefaultModelInstanceId` |
| MCP Workflow 调用 | 读取发布 GraphSpec 后，将调用方 `arguments` 直接交给执行器，未注入发布默认模型 |
| Automation Workflow 调用 | 将发布 GraphSpec 与 `input` 交给执行器，未从发布快照组装该默认模型 |

证据：[Supervisor 快照读取](../../reachai-runtime-service/src/main/java/com/enterprise/ai/runtime/supervisor/AgentScopeSupervisorRuntimeAdapter.java)、[上下文设置](../../reachai-runtime-service/src/main/java/com/enterprise/ai/runtime/supervisor/AgentScopeSupervisorRuntimeAdapter.java)、[MCP 执行入口](../../reachai-runtime-service/src/main/java/com/enterprise/ai/runtime/mcp/application/RuntimeMcpToolExecutionService.java)、[Automation 执行入口](../../reachai-runtime-service/src/main/java/com/enterprise/ai/runtime/automation/RuntimeAutomationTargetExecutor.java)、[模型节点选择规则](../../reachai-runtime-service/src/main/java/com/enterprise/ai/runtime/execution/kernel/RuntimeModelNodeHandlers.java)。

本地使用同一 LLM 图、真实 MCP 业务服务和真实 GraphSpec 执行器，替换存储与模型传输：

| 场景 | 实际结果 |
| --- | --- |
| 执行器收到发布默认模型 `published-model` | 成功，模型请求使用 `published-model` |
| MCP 发布快照有该默认模型，调用参数没有模型字段 | 失败，`RUNTIME_GRAPH_MODEL_REQUIRED` |
| MCP 调用参数添加 `modelInstanceId=caller-selected-model` | 成功，模型请求使用调用方指定模型 |

证据：[复现程序](../../output/tasks/architecture-audit-20260905/RuntimePublicationDefaultsAudit.java)、[运行结果](../../output/tasks/architecture-audit-20260905/RuntimePublicationDefaultsAudit.result.json)。Automation 本轮只有源码对照，尚未运行同样的入口级复现。

目标设计：由 Workflow owner 将固定发布版本解析为不可变执行目标，统一组装 GraphSpec、版本、默认模型、资源配置和项目范围。各调用入口补充自己的可信身份及业务输入，再交给执行门面。模型节点覆盖规则保持一致，普通业务输入不能静默替代发布配置。执行内核继续依赖显式契约，不反向读取 Workflow 表。

### R3：发布审计身份需要绑定可信操作者

[Control 发布与回滚入口](../../reachai-control-service/src/main/java/com/enterprise/ai/control/runtime/ControlRuntimePublicController.java) 检查权限后原样转发请求体。[Runtime Controller](../../reachai-runtime-service/src/main/java/com/enterprise/ai/runtime/api/RuntimeWorkflowVersionPublicController.java) 从请求中读取 `publishedBy` / `operator`，最终在 [版本服务](../../reachai-runtime-service/src/main/java/com/enterprise/ai/runtime/workflow/RuntimeWorkflowVersionService.java) 写入发布记录；回滚还会覆盖所选历史版本的发布人和发布时间。

这使记录中的发布人可以为空、是页面名称，或由具备操作权限的调用方自行填写。当前 [Controller 测试](../../reachai-runtime-service/src/test/java/com/enterprise/ai/runtime/api/RuntimeWorkflowVersionPublicControllerTest.java) 也明确验证了请求中的 `alice` / `bob` 被原样传给服务。相较之下，[能力评审入口](../../reachai-control-service/src/main/java/com/enterprise/ai/control/capability/CapabilityReviewConsoleController.java) 已从平台会话解析操作者。

目标设计：操作身份从可信会话或受信任的系统身份产生；用户备注与操作身份分别存储。版本原始发布信息保持可追溯，发布、回滚、重新激活作为独立操作事件记录。这里确认的是审计字段可信度问题，没有将其扩大为权限校验失效。

### R4：发布、保存、回滚需要统一修订语义

[Studio 发布 composable](../../ai-admin-front/src/views/workflow/composables/useWorkflowStudioRelease.ts) 提交 `baseRevision`；[版本管理页](../../ai-admin-front/src/views/workflow/WorkflowVersions.vue) 发布时不提交该字段。[后端版本服务](../../reachai-runtime-service/src/main/java/com/enterprise/ai/runtime/workflow/RuntimeWorkflowVersionService.java) 在缺失时选择不带修订条件的更新；[定义服务](../../reachai-runtime-service/src/main/java/com/enterprise/ai/runtime/workflow/RuntimeWorkflowDefinitionService.java) 也明确保留该分支。[回滚请求](../../reachai-runtime-service/src/main/java/com/enterprise/ai/runtime/api/RuntimeWorkflowVersionRollbackRequest.java) 只有操作者，没有基础修订。

因此，同一份草稿的防覆盖保障取决于入口。版本表 [新库基线](../../sql/initV2.sql) 约束了 `(workflow_id, version)` 唯一，尚未提供单一 ACTIVE 版本的独立数据库约束；当前发布先查询并退役 ACTIVE 版本，再插入新版本。

目标设计：先明确“发布看到的哪份草稿”“回滚是否覆盖当前草稿”“单一活动版本”三个不变量，然后统一公共命令的修订检查。后台任务如需无交互发布，应使用明确的系统命令与并发控制，不通过缺省参数隐式放松保障。

已确认入口契约不一致；两个发布事务能否实际留下多个 ACTIVE 版本、回滚与编辑如何争用，仍需 MySQL 并发测试。本轮没有把推演结果写成数据库复现事实。

## 5. 架构与维护问题

### R5：检查规则需要覆盖真实边界

检查器还有两处已复现的盲区：

- [循环检查](../../scripts/check-internal-module-boundaries.mjs) 只识别 A → B → A。A → B → C → A 的最小反例返回成功，并显示 `0 cycles`。

证据：[反例程序](../../output/tasks/architecture-audit-20260905/check-boundary-blindspots.mjs)、[反例结果](../../output/tasks/architecture-audit-20260905/boundary-blindspots.json)。现有检查器测试通过，证明现有测试尚未覆盖这两个反例。

目标设计：检测完整有向依赖图；按声明类型和持久化职责识别 Mapper/Entity，而非仅依赖目录名。分别记录“直接双向依赖”和“包含多个模块的循环组”，避免把不同统计口径混成一个数字。原有禁止回流边继续生效；新发现的存量问题逐调用点登记并安排消除，不能整体豁免服务或目录。

### R6：收回模块内的数据访问和公共契约

对实际 Java import 图进行强连通分量分析后，Control 虽没有直接双向依赖，仍有两组较长的循环：

1. `aicoding → client → pageworkbench → aicoding`；`identity` 也位于同一四模块循环组。
2. `aiassist → platform → runtime → aiassist`。

第一组可追踪到 [AI Coding 引用 client](../../reachai-control-service/src/main/java/com/enterprise/ai/control/aicoding/application/AiCodingTaskApplicationService.java)、[RuntimeProxyClient 引用页面工作台 DTO](../../reachai-control-service/src/main/java/com/enterprise/ai/control/client/runtime/RuntimeProxyClient.java) 和 [页面工作台调用 AI Coding](../../reachai-control-service/src/main/java/com/enterprise/ai/control/pageworkbench/application/PageWorkbenchWorkflowDeliveryApplicationService.java)。集中式 `client` 包同时承载多个业务适配器，使局部依赖倒置仍可能在顶层模块图上闭环。

Runtime 观察到既有 9 组直接双向依赖；进一步分析得到一个涉及 10 个模块的循环组，以及 `memory/supervisor` 二模块循环组。这里统计的是包含契约和适配器的 Java 包依赖，不是 Spring Bean 构造环，也没有据此推断服务运行时互相递归调用。

持久化越界的明确例子包括：

- [Agent 执行上下文解析器](../../reachai-runtime-service/src/main/java/com/enterprise/ai/runtime/agent/RuntimeAgentExecutionContextResolver.java) 直接持有 Workflow/A2A Mapper 与 Entity。
- [Workflow 定义服务](../../reachai-runtime-service/src/main/java/com/enterprise/ai/runtime/workflow/RuntimeWorkflowDefinitionService.java) 反向读取 Agent 的 Workflow-as-Tool Mapper，用于判断可删除性。
- [能力影响分析服务](../../reachai-control-service/src/main/java/com/enterprise/ai/control/capability/CapabilityChangeImpactService.java) 直接读取 MCP/A2A 发布持久化类型，对应诊断中的 7 处违规。

目标设计：先抽出拥有业务语义的只读查询端口和不可变快照，保持现有批量查询能力。按“Agent 引用 Workflow”“能力变更查询外部发布影响”等具体链路整理；持久化仍留在其 owning module。服务边界保持现有五服务拓扑。

### R7：引用证据查询需要稳定的读取模型

[RuntimeCapabilityReferenceService](../../reachai-runtime-service/src/main/java/com/enterprise/ai/runtime/internal/RuntimeCapabilityReferenceService.java) 每次检查读取 Workflow 定义、发布版本、Agent 与绑定表，各取最多 10,001 行，并解析图内容。[Control 聚合](../../reachai-control-service/src/main/java/com/enterprise/ai/control/capability/CapabilityChangeImpactService.java) 读取已发布 MCP/A2A，再逐发布查询修订。它由能力变化列表请求触发。

当前实现能把超限或证据异常标记为不完整，保守语义值得保留。需要改进的是请求成本随全库和发布历史增长，以及读取模型由多个模块内部结构共同决定。本轮没有测量真实延迟或吞吐量。

目标设计：由 owner 提供批量引用查询，逐步建立按能力反查 Workflow/Agent/发布修订的读取模型，并明确刷新、失效和完整性语义。能力可能被跨项目引用，不能仅增加一个项目过滤条件而丢掉真实引用。
