## 必须保持的约束

1. 外部写入之前提交执行清单。登记失败时不调用 Milvus。
2. 发布和回收必须在同一执行记录上互斥；清理只能处理已失去发布资格的执行。
3. 回收只使用该执行的确定性主键，不使用 file_id 整文件删除。
4. 发布事务同时确认任务、文件、知识库、租约和执行清单，并把执行标记为已发布。
5. 超时和进程消失不等于远端写入结束；一次删除成功不允许永久遗忘仍可能迟到的写入。
6. 重启和多副本调度必须可继续，删除失败不能丢失待回收身份。

## 持久化模型

已新增 `knowledge_document_index_execution`，唯一 owner 为 `reachai-knowledge-service`。每次写入一行，以独立执行身份为主键，任务写入使用本次租约身份；保存 operation_type、可空 job_id、file_id、knowledge_base_id、collection_name、vector_prefix、vector_count。非任务操作为 DIRECT、PIPELINE 或 REEMBED，另保存 publication_deadline；重新向量化保存原文件/片段内部 ID、原向量/集合身份及正文 SHA-256。RETIRED_VECTOR 记录被替换向量的准确 single_vector_id，批量前缀为空。

主键清单由已固定的 vector_prefix 与 `[0, vector_count)` 重建，避免保存正文或巨大的 JSON 数组。登记后身份字段不可修改；同执行再次登记必须核对完全一致，不能覆盖原清单。

控制字段至少包含 state、write_acknowledged、cleanup_cursor、next_cleanup_at、cleanup_lease_owner、cleanup_lease_until、last_cleanup_error、create_time、update_time。日期和调度判断以数据库时间为准。

状态为 REGISTERED、PUBLISHED、RECLAIMING、RECLAIMED。PUBLISHED 不进入失败回收。只有能够证明外部写入已确认完成且整批删除成功的执行，才能从 RECLAIMING 进入 RECLAIMED。

## 写入、发布与回收顺序

登记事务按知识库行 → 任务行（如有）→ 执行行 → 文件/片段行加锁，确认租约或非任务目标、文件和知识库归属，并核对提交快照、上下文和清单的物理集合一致，独立提交后才执行外部 upsert。任务缺失快照时不推断目标，必须重新提交。相同执行只允许同一份不可变清单；仅首次插入成功的调用取得一次写入许可。重复登记不重新 upsert，防止先返回的写入确认掩盖仍在途的第二次请求。Milvus SDK upsert、createCollection 和 dropCollection 使用独立配置关闭自动重试。

MySQL 的 CURRENT_TIMESTAMP 取语句开始时间。取得任务行锁后使用第二条锁定读重新校验有效期，并关闭这条校验的 MyBatis 缓存，避免等待锁穿过截止时间时仍被放行。

直接 chunk 导入、非任务流水线和重新向量化均生成新的服务端 UUID，以 `<64hex>_chunk_i` 形成独立主键，不再使用基于 fileId 的固定命名域或重复写入旧向量主键。非任务登记在数据库中设置 20 分钟发布截止时间；失败时持久化撤销发布资格，进程退出则由截止时间驱动恢复。外部 Embedding/Milvus 调用不持有数据库事务。

重新向量化发布时核对原文件内部 ID、片段 ID、原向量/集合身份和正文摘要；正文变化、文件删除重建或另一轮替换都会拒绝旧结果。仅更新向量引用，保留并发标题、启用状态和命中计数。片段编辑和启用操作也只更新其负责的字段，不能把读到的旧向量引用写回。

旧向量回收记录与新引用、PUBLISHED 状态在同一事务提交。准确旧主键若可关联已确认且已发布的原执行，完整删除后可结束；历史主键没有该证据则持续复查。回收前发现同集合/主键仍被其他片段引用时退避，不删除仍使用的向量。

外部 upsert 成功返回后记录 write_acknowledged。异常或超时不记录成功确认。进程在成功返回后、确认落库前退出时，保守地视为结果未知。确认落库同时清零回收 cursor 并撤销当前回收租约，确保迟到写入覆盖已删除前缀时，需要重新完整扫描才能结束。

元数据事务保持统一锁顺序：知识库行 → 任务行（如有）→ 执行行 → 文件行 → chunk 行。确认清单身份和发布资格，写入文件和 chunk，更新执行 PUBLISHED；任务写入还同时更新任务 COMPLETED。任何一步失败都回滚。非任务发布在执行行锁获得后重新查询数据库截止时间，最终 publish SQL 也再次校验期限。

失败或租约恢复可先清空任务租约；执行表保留旧租约身份。回收按相同知识库、任务（如有）、执行顺序加锁，核对该执行已失去发布资格，转为 RECLAIMING；已登记的回收不要求知识库仍存在。调度器每轮最多 8 个执行，每个批次最多 100 个准确主键，删除在事务外执行；每条成功删除后以租约身份和旧 cursor 条件保存进度并续租 60 秒。即使调用跨越截止时间，只要没有新 owner 接管仍可保存进度；一旦 owner 改变立即停止旧批次。删除失败退避 30 秒，未知写入完整扫描后退避 300 秒。多副本重复删除幂等。

如果 write_acknowledged 为真，删除完整清单后可标记 RECLAIMED。否则删除完整清单后重置 cursor 并安排下一轮复查，继续保留执行记录。这样远端迟到写入仍会被后续回收，而不是在一次空结果后成为永久孤儿。不能凭任意等待时长认定写入已经结束。

保守保留的未知执行会有持续存储和调度成本。第一版使用有上限的批次和退避，不自动删除未知执行记录；未来只有增加可验证的远端完成证据，才收紧保留规则。

## 知识库集合创建与退场

`knowledge_collection_lifecycle` 保存物理集合身份、业务 code、维度、发布后的知识库内部 ID、创建截止时间和回收租约，唯一 owner 为 Knowledge。新增创建先独立登记 CREATING，20 分钟发布期限由数据库设置；随后在事务外 ensure，确认返回后独立保存 ACK，最终将知识库元数据和 READY 状态在同一事务发布。整个创建流程挂起外层事务，其已提交结果不受调用方之后回滚影响。元数据插入失败或发布过期时持久化退场，不凭内存结果删除可能已提交的知识库。

发布先锁集合记录，再以独立锁定查询采样当前数据库时间，防止等待行锁后使用过期资格。回收也先锁同一集合记录；随后非锁定查询知识库与 chunk 的物理引用，不先取得知识库空范围的间隙锁，避免与发布插入形成反向锁序。真实 MySQL 双连接已验证发布/回收交错和锁等待后的期限校验。

整体删除在知识库事务内统一退场文件、索引执行、任务和权限，再删除问题、标签并保存集合退场状态；命中历史保留。远端 drop 不在删除事务中执行，因此数据库回滚不会提前破坏集合。回收只针对保存的物理身份，同业务 code 新建库取得另一物理身份。向量写入步骤不再自动 ensure，不允许迟到索引流程重新创建旧集合。

集合调度独立于导入 Worker 开关，默认每 10 秒最多处理 8 条，配置为 `reachai.knowledge.collection-cleanup.enabled` 与 `reachai.knowledge.collection-cleanup.interval-ms`。存在知识库或 chunk 引用时退避；认领 60 秒租约后在事务外 drop，完成时核对 owner。失败保存错误类型并退避 30 秒；创建结果未知时，完整删除后仍保持 RECLAIMING，300 秒后复查。迟到 ACK 撤销旧租约，旧回收不能结案。只有创建已确认且 drop 成功才可结束；存在性查询的异常和空响应不等同集合不存在。

历史映射只保存已知物理身份，不推断创建完成或未知维度。历史未登记集合在删除时也保存保守回收意图。未知创建的持续扫描会占用调度资源，当前不凭等待时长或一次不存在响应删除记录。业务索引集合仍属于独立的后续治理范围。

## 原件与解析工件

工件由 ManagedDocumentArtifactStore 统一登记后端与准确对象身份，物理写入前提交 WRITING，确认后才能原子发布引用。业务退场与 RECLAIMING 同事务，回收保留所有文件和未完成任务引用。独立调度使用租约与退避；未知写入持续复查，迟到 ACK 撤销旧租约。具体配置、本地身份与 S3 分片/版本回收边界见 [文档入库契约](../architecture/docling-document-ingestion.md)。

## 标签目标与父子关系

KnowledgeTagService 统一查询、统计和变更；变更先锁当前知识库，再锁定读取目标与父标签，避免在 MySQL 锁等待后使用旧快照。单条/批量创建共用规范身份与去重规则。文件删除、同一导入任务替换元数据时清理 FILE/CHUNK 标签，存活子标签解除父引用，全部变更随元数据一起提交或回滚。整库删除沿用原子清理本库全部标签的边界。

## 问题引用与知识库身份

KnowledgeQuestionService 统一问题查询与变更。创建先锁原知识库，再当前读取并锁定片段；文件和整库退场使用同一知识库锁，等待结束后不会接纳已删除的原身份。文件删除和同一导入任务替换片段只解除原片段引用，保留问题文本与命中次数，整库删除清理本库全部问题。所有引用变更和元数据提交、回滚保持一致。

## 共享检索与内容授权

Runtime、RAG 和查重共用 KnowledgeRetrievalCore。PermissionService 创建服务器端记录身份快照，在重排前、结果返回前及 RAG 生成前后重新查询当前授权和片段，校验原身份、正文及启用状态。短事务使用 READ COMMITTED，外部模型调用不占用本组件的数据库事务。管理员检查共享检索引擎并保留独立管理授权入口；快照不能通过 HTTP JSON 提供或返回。

## 业务删除与向量生命周期的剩余边界

本节第 1 至 7 项已覆盖文档/片段索引、文件删除与替换、知识库整体删除及集合创建回收。原件/解析工件的持久化清理另已接入；解析临时 JSON 已通过本机进程中断验证，主键复用已由不可变记录身份隔离；S3 工件回收路径已实现版本正文和删除标记清理；同版本本机 MinIO 已通过真实存储验证，开发库已结案登记为 0；部署环境、其他环境历史回补、整库恢复、部署文件系统与历史孤立资源仍待验收或治理；进行中检索已复核原记录身份，文件标签和知识问题引用现已纳入相同元数据事务，不能据此宣称所有资源均已具备完整生命周期保障。

当前 [KnowledgeFileDeletionService](../../reachai-knowledge-service/src/main/java/com/enterprise/ai/service/impl/KnowledgeFileDeletionService.java) 统一两个文件删除入口及整库文件退场，事务中保存向量回收意图、取消关联任务、删除引用和权限；重解析发布同时退场原文件。后台回收只使用登记的准确主键，并保留仍被片段引用的向量。KnowledgeServiceImpl 将整库创建和删除委托给生命周期组件；数据库事务不再包含集合创建或 drop。

实施顺序和约束：

1. 已实现任务导入、直接导入、同步流水线和重新向量化统一登记。每次操作取得新的执行身份和向量主键，只允许一次 upsert。非任务执行保存操作类型、发布截止时间；任务 ID 可空。固定命名域实现已退出，所有新增文档/片段向量均先登记。
2. 重新向量化先写新向量，成功后再事务性替换 chunk 引用。登记时捕获 chunk 内部 ID、原 vectorId 和正文摘要，发布时重新核对；文件被删除重建、正文更新或另一轮替换后，旧结果失去发布资格。不能在新向量成功前删除当前可用版本。
3. 所有登记、发布和业务删除按知识库行 → 任务行（如有）→ 执行行 → 文件行 → chunk 行加锁；批量锁按稳定 ID 排序。外部 Embedding/Milvus 调用放在事务外。已经 RECLAIMING 的记录继续独立回收，不要求知识库仍存在。
4. 两个文件删除入口和知识库整体删除使用同一文件退场组件。事务内撤销旧执行发布资格、将其转为 RECLAIMING、取消尚未完成的关联任务，并删除业务引用与文件权限；文件单独删除保留独立问题正文并解除 chunk 关联，整库删除则移除该库问题和标签。删除后同 fileId 的新导入使用新的执行身份；数据库唯一约束限制跨知识库活动占用，并允许已完成/已取消任务保留历史。重解析保存提交时原文件内部 ID 与不可变记录身份，发布时核对并原子退场；后台只清理已登记的准确主键，不按 fileId 整批删除。
5. 历史 chunk 的准确 vectorId 必须在删除数据库引用之前保存为回收依据。不能从任意历史 ID 猜测 prefix/count；执行清单可增加单向量 ID 表达式，且保持一次写入/一次身份的语义。
6. 业务 code 与物理 collection 身份分开。本项已实现：新知识库使用不可复用的物理集合名，现有库记录其当前实际集合名；流水线上下文、执行清单、检索、去重、chunk 元数据和补偿分别保留业务 code 与物理集合名。旧集合的迟到 drop 只作用于旧物理集合。异步任务持久化提交时的物理集合快照，并在重试、正式入库、执行、登记和发布时核对，覆盖相同数据库 ID/code 重建的情况；缺失的历史快照不推断回填。
7. 集合创建和删除已使用持久化清理意图，createCollection/dropCollection 禁用隐式 SDK 重试；超时、鉴权错误不能当成“不存在”。创建未知时继续清理旧物理集合；索引写入入口不再 ensure。集合已确认完成并退场后，迟到 upsert 无法重新创建集合；未知索引执行仍保留自己的准确主键回收记录。
