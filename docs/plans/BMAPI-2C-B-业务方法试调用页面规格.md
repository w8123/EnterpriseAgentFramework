# BMAPI-2C-B 业务方法试调用页面规格

更新时间：2026-09-16。状态：2C-B 已通过[主任务最终复核](../../output/tasks/business-method-api/BMAPI-2C-B-主任务复核.md)，限代码、组件测试与隔离浏览器证据。真实业务系统与部署环境尚未完成端到端验收；当前进度转入 2D Workflow 接入。

关联[实施基线](./业务方法与API重构实施基线.md) U1 第 4 步、U2 第 3 步；调用行为以 [2C 总规格](./BMAPI-2C-业务方法试调用规格.md)和已复核的后端契约为准，当前完成情况见[实施进度](./业务方法与API重构实施进度.md)。

## 1. 用户要完成的任务

从一个明确的业务方法出发，看清调用目标、准备输入、确认操作影响、执行一次，并理解返回或失败原因。响应丢失后能找回原尝试，不靠重新执行来查询结果。

本批在现有详情内增加试调用，复用已完成的 owner context / invocation / query 接口。不做独立“调试工具”菜单、权限管理页面、实例选择器、用户身份桥接或 Workflow 编辑器。旧混合能力 / API 详情不得因此出现调用业务方法接口的按钮。

## 2. 页面结构与共享归属

延续 [DESIGN.md](../../ai-admin-front/DESIGN.md) 和 [UX-CONTRACT.md](../../ai-admin-front/UX-CONTRACT.md) 的高密度工作台、现有字体和主题 token。沿用业务方法详情的双栏结构，不新增全屏工作台或改变全站样式。

- 具体入口：`CapabilityDetailDialog.vue` 在 `catalogKind=business-method` 时增加“试调用”页签或页签入口，位于“输入与返回”之后；也可在右侧调用状态区放“试调用”按钮切换到该页签。两者进入同一面板。
- 面板拆为方法领域组件与 composable，避免把 HTTP、状态机、输入解析、存储和 DOM 全塞入现有详情文件。
- 上方是方法名称、所属项目、安全目标摘要、身份模式和副作用；中部为输入；提交区后紧接本次结果。目标信息在提交前可见，不藏入“技术信息”。
- 原有详情的说明、来源、使用位置和技术信息继续工作。窄屏使用单列和明确的内容滚动区，不通过全局 `overflow:hidden` 隐藏内容。
- Overlay 使用 `AppDialog` / 现有共享 owner；表单用 Element Plus / 现有应用表单，状态用 `StatusTag`，短反馈用 `ElMessage`。持久错误放在面板内，不能只放 Toast。日期、复制、权限与账号状态复用既有工具。
- 参考现有 `useWorkflowStudioDebugSession.ts` 的尝试引用与迟到响应隔离原则，但不复制 Workflow 身份或接口，也不要求先创建 Workflow。

## 3. 上下文、权限与目标

1. 使用现有 `controlRequest`（session / CSRF）访问 2C 的三个公共 API，定义明确的 TS DTO；不从前端直连 Runtime / Capability，不使用通用旧 tool/test 入口。
2. 新增对应 `capability:invoke` 前端权限常量，复用 `platformAccess` 的全局/项目 grant 判断；实际 ACL 与可执行性由 invocation-context 及 POST 再核验。缺权限时不给可执行动作，可显示普通文字说明；不提供一键授权。
3. 进入试调用时读取最新 invocation-context，锁定 canonical method / project / expectedContractHash。loading、403、404、来源变化、停用、凭据不可用、需要业务身份分别表达，不凭旧列表状态启用提交。
4. 调用身份的固定说明为“使用项目接入凭据调用；不携带业务用户身份，业务系统仍会校验”。目标来自 owner 的安全摘要；不展示或编辑 token、URL、实例、业务用户或角色。
5. 准备阶段的失败可以“重新读取调用条件”；此动作只能 GET，不能触发调用。刷新后 hash 改变必须清除旧确认，不能自动重发。

## 4. 输入体验

- 简单、已知的标量参数提供紧凑表单；复杂对象、开放 Map、数组或无法无损表示的输入提供 JSON 编辑。保留明确的“表单 / JSON”方式，切换不能丢字段、改变数值/布尔类型或悄悄插入包装层。
- 使用 owner 返回的逻辑参数树。单 DTO 的平铺/包装按后端已验证语义处理，默认表单采用平铺对象；多个方法参数仍按各自参数名。标识为 `userId` 的普通输入只是业务参数，不是调用身份。
- 空参方法显示“无需填写参数”，发送 `{}`。可选参数的“未填写”与 false、0、空字符串、null 分开，不擅自代填。
- 样例/默认值来自来源声明，只通过显式“填入样例”采用；不自动执行或生成业务数据。对象/数组样例保持 JSON。敏感字段不提供来源样例/默认值，标量输入默认遮盖；完整原始 JSON 的显示/编辑必须是显式操作，并可重新遮盖敏感内容。
- 本地检查 JSON object、可确定的 required/类型等，服务端 owner 校验仍是最终依据。已声明但当前无法验证的形态明确显示限制，不能提示“所有参数已验证”。
- 将安全 `inputDiagnostics` 的 path/reason 映射为简体中文文字并关联字段；JSON 模式至少显示字段路径和原因。不要把内部码或原始异常当主要文案。
- 无效输入保留用户编辑内容并定位错误；同一表单与 JSON 模式的值以一个内存状态为准，禁止日志、URL、localStorage、埋点和原始输入复制按钮。

## 5. 一次提交与副作用确认

| 条件 | 用户动作与行为 |
| --- | --- |
| READ / READ_ONLY / NONE | 参数检查通过后“开始试调用”，无额外写入确认 |
| 写入 / 不可逆 / 未知副作用 | 明确显示“可能修改业务数据”，应用自有确认展示方法与目标；以“确认并调用”为最终动作，默认聚焦取消 |
| context/hash/输入被修改 | 上一次写入确认失效，需要重新确认当前尝试 |
| 已在提交或等待结果 | 锁定本次请求快照与调用按钮；重复点击、回车或双击不能产生第二个 POST |

- 用户最终确认后、POST 发出前，生成 UUID invocationId 并保存归属明确的尝试引用。一次尝试仅主动 POST 一次；不得加入自动重试、错误重放或刷新后重新 POST。
- 请求体只包含 invocationId、expectedContractHash、input、confirmedSideEffect。调用目标和身份不由浏览器补充。
- 超时、断连、取消前端等待、无法识别的答复都不能证明没有执行；保留原 ID，进入只读查询状态。401 按现有会话失效处理并清除当前编辑和结果，不能保留为新账号的草稿。
- 仅当服务端明确说明 NOT_DISPATCHED 或已知提交前拒绝，才提示修改条件后新建尝试；新尝试使用新 ID。未知结果若用户明确要重新发起，先提示上一尝试可能已经生效，写入方法须重新确认；该操作不能叫“重试”。

## 6. 结果与恢复

| 服务端事实 | 主要文案与动作 |
| --- | --- |
| ACCEPTED / PERSISTED | 已接纳，等待派发；可以“查询本次结果” |
| DISPATCHING | 正在调用；显示原尝试，可查询；不重新提交 |
| SUCCEEDED | 调用成功，展示处理后的业务返回、耗时与关联记录 |
| BUSINESS_FAILED | 业务处理失败；展示处理后的业务返回，不能宣称没有发生变更 |
| NOT_DISPATCHED | 本次未发起业务调用；说明实际拒绝原因与修正入口 |
| UNKNOWN，或 POST 未取得可信结果 | 本次结果尚未确认；明确“可能已执行”，主动作只查询原记录 |
| 查询失败 / 暂未查到 | 保留原 ID，说明查询未完成；不把 404 当作允许重发的依据 |
| resultExpired / 截断 | 显示真实状态及“结果已过期”或“结果已截断”；不伪造空返回，也不重新执行 |

- 本批使用手动 GET 查询与重新打开时一次只读恢复，不建无限轮询。GET 按钮单独有 loading 与失败恢复，不清空已有安全结果或改写原 invocationId。
- 结果显示服务端处理后的 JSON，复制只复制该副本。诊断/状态 metadata 与业务返回保持清楚的视觉层次，输出 schema 缺失时仍可展示实际 JSON。
- 提供 invocationId 与 runId/traceId 的复制，以及服务端结果有效期。没有 RunOps 权限也能在本面板查看自己有权查询的结果和阶段；只有当前项目 RUNOPS_READ 才提供现有 RunOps 详情链接，不绕过其路由授权。
- 尝试引用以登录账号 + canonical project + method 隔离，仅保存 ID 和必要的归属/时间，不保存参数、结果、target URL 或凭据。每方法最多保留最近 5 个引用，以简短列表恢复；不新增独立历史管理页。
- 关闭、卸载、账号/项目范围/方法切换时清空输入、结果及在途 UI 状态，保留允许的引用供同账号恢复。每次上下文世代变化都废弃旧回调，A→B→A 也不能接纳旧 A 响应或误删新引用。
- 手动关闭有未提交输入时使用应用自有丢弃确认；账号失效或范围切换立即清理，不用确认阻塞隔离。已发出调用的面板可关闭，但明确关闭不会取消业务执行；重开只查询。

## 7. 实施范围与验证

允许改 `ai-admin-front` 的方法详情、方法调用领域组件/composable、API/类型、权限常量、测试及相应 UX 契约条目。若页面发现后端契约无法满足已确定行为，先给具体反例，再做本批最小修正与后端回归；不扩大为全站权限/导航/组件治理。

执行任务先按已安装的 frontend-design 与 frontend-design-premium 技能读取相关 references，确认既有 canonical owner。记录本批行为取舍，不另造 DESIGN.md、不修改既有视觉身份来迎合一页。

最低验证证据：

1. 相关状态/组件测试：上下文加载/失败/不可用、简单与复杂输入、平铺/包装、敏感输入显示与模式切换、无效 JSON 和服务端字段诊断。
2. 写入确认、确认失效、双击/回车只发一次、POST 超时/断连保留 ID、GET 404/失败不 POST、重开与浏览器刷新只读恢复、UNKNOWN 显式新建尝试。
3. 账号/项目/方法切换、切走再切回、关闭后迟到答复、存储不可用，均不泄露旧输入/结果或误写引用；无权限与撤权的动作/结果处理。
4. 使用实际页面的浏览器证据覆盖成功、业务失败、未派发、未知结果、过期/截断、长 JSON、键盘焦点和恢复、窄屏 768px 及 200% 缩放。fixture 必须与真实 DTO/lifecycle 一致，保留请求日志证明只发预期 POST/GET。
5. 至少一次浏览器路径连接隔离的真实后端执行链或已复核的本地 SDK fixture，明确经过哪些组件；纯页面拦截仅作为 UI 验证，不能冒充业务 E2E。若受服务构件限制，用独立端口测试宿主，不能擅自重启既有服务、升级开发库或改真实授权。
6. 相关 Vitest、vue-tsc、`npm run build`、Premium strict audit、相关架构/文档/路径检查与 `git diff --check`。既有无关 UI 守卫失败单列，不能为了通过本批去改无关 WIP；任务触及的缺陷须修复。
