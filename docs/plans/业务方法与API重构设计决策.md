# 业务方法与 API 重构设计决策

更新时间：2026-09-15。状态：主任务依据 BMAPI-1A 映射及关键源码复核确定实施方向；本文件不是实现或真实调用验收证据。执行位置见[实施进度](./业务方法与API重构实施进度.md)。

依据：[实施基线](./业务方法与API重构实施基线.md)、[BMAPI-1A 现状映射](../../output/tasks/business-method-api/BMAPI-1A-现状映射.md)。主任务重点复核了 Starter 发现与注册、来源 intake/projection、Control ACL 和 Runtime MCP 执行边界；未运行测试或真实调用。

## 1. 已选定的设计

### Q1：方法声明和 HTTP 映射分别表达调用契约

- `@ReachCapability` 明确声明业务方法，继续通过 SDK 的方法调用入口执行；不因它位于 Controller 中就静默改成 HTTP API。
- 实际 Spring MVC 映射描述 HTTP API，按 HTTP 请求/响应契约处理；声明了方法注解也不能在最终模型中丢掉 HTTP 来源证据。
- 同一 Java 实现可以提供两种调用契约。两者各有稳定身份、参数位置、调用条件与引用，通过同一实现的来源信息关联；不是在两个目录自由编辑同一份定义。
- API 扫描不会自动创建业务方法，方法存在也不意味着另一条 HTTP API 已验证、已授权或自动对外发布。
- 双重声明在 BMAPI-3 实现完整分流；BMAPI-2A 仅增加明确类型，不改变现有路由、名称或 MVC skip 行为。该阶段限制必须报告，不能提前宣称双重声明已修复。

### Q2：明确类型，保留稳定源引用

- 资产类型取值为 `BUSINESS_METHOD`、`HTTP_API`；缺乏明确声明的旧对象使用技术状态 `UNCLASSIFIED`，不在产品中伪装成业务方法。
- 类型由来源契约携带。SDK 描述符使用明确类型，注册运输层使用既有 `metadata.assetType` 字段；Capability 对字段值进行统一校验，不让前端通过 URL、标签、`source=sdk` 或 HTTP 传输方式猜类型。
- 现有快照、接纳决定、来源状态和 accepted contract 仍共同维护契约事实；调用投影从已接纳契约生成。
- 在扫描目录行和调用投影增加 `asset_type` 作为可筛选投影；其值由来源应用过程统一写入，不是第二处可编辑的业务事实源。
- 首批保留现有方法 `projectCode:name`、technical storage name 和发布引用。类型声明进入既有 metadata 差异与 contract hash，发生变化时沿现有漂移与接纳规则处理。
- 缺少类型的旧输入保持其原契约 JSON，不为了填 `UNCLASSIFIED` 改写 metadata 或批量重算哈希；数据库投影默认未分类，可信重新同步后再形成类型证据。
- API 后续以所属逻辑服务、HTTP method、完整路由模板及必要 mapping conditions 确定操作身份。Controller/OpenAPI 多来源关联必须比对完整契约；规范化名字相同不能视为同一接口。具体有界编码和冲突规则在 BMAPI-3 规格中明确，不改动现有业务方法引用。

### Q3：来源拥有契约，平台拥有接纳与使用配置

- 来源拥有类型、方法或 HTTP 入口、输入输出、原始业务说明与声明的副作用等契约字段；SDK 来源保护继续生效。
- 平台拥有接纳决定、允许的使用配置及平台补充信息。补充展示内容独立存储并明确来源，不覆盖来源声明，也不把 AI 生成说明当作已核实事实。
- HTTP 方法、参数位置或返回契约不完整时保留具体缺口，不自动推断成可调用契约。
- 当前不增加平台覆盖风险等级、权限或来源契约的捷径。

### Q4：管理端使用独立试调用入口，复用受控执行机制

- 管理端试调用应有自己的 Control 公共入口与 Runtime 内部执行入口；用户无需先创建 MCP 发布才能试一个业务方法。
- 复用可信身份构造、项目归属核验、Control ACL 决策、Capability 来源/契约保护及 Runtime Run/Trace 基础。MCP 是已核对的实现样板，不把管理端伪装成 MCP 客户端，也不复制整套执行引擎。
- ACL 只有明确 `ALLOW` 才能执行；`SKIPPED`、无角色、无匹配或查询失败不能当作允许。身份、角色、项目和目标契约由服务端核实，不能从试调用请求体采信。
- 客户端不选择任意 URL 或伪造执行身份。输入引用明确环境中的目标资产与预期契约；服务端核对当前定义，返回真实状态、runId/traceId 与可理解的错误。
- 写操作提示实际影响，执行与确认按实际副作用区分；不可重试的操作不自动重发。基本保护在入口交付时成立。
- 2026-09-16 已具体化为 [BMAPI-2C 规格](./BMAPI-2C-业务方法试调用规格.md)：平台 actor 负责审计与 Console 授权，项目凭据调用不映射业务用户；新增 capability:invoke 并要求现有 ACL ALLOW；沿用含 baseUrl 的已接纳契约，不另选健康实例；Runtime 使用独立 CONSOLE_CAPABILITY Run 与持久去重 / 结果记录。
- 结果未知先查询原记录，写操作显式确认，统一不自动重试。安全结果默认保留 24 小时，幂等身份不因结果过期消失。先交付 2C-A 后端与隔离真实 HTTP 证据，再接 2C-B 页面；不改变真实权限或数据库。

### Q5：API 来源逐步接入同一资产使用路径

- Controller、OpenAPI 与外部 API 市场分别保留来源；共同进入 API 资产的候选、契约验证、接纳和使用过程。
- 扫描发现、市场收录、项目接入意图、接入配置完成、真实验证成功分别表达，不能复用 `READY` 文案证明 Runtime 可执行。
- 旧 promote 流程在 API 路径覆盖后退场；调用投影仍可保留，人工重复维护不保留。
- 外部 API 从 Operation 到执行的缺口属于 BMAPI-3 的明确工作项，不扩建市场，也不从专项总范围删除。

### Q6：增量演进；数据处置依据真实情况

- 首批仅新增类型投影字段和索引，保留已有主键、稳定名称与发布引用。同步维护新库基线和当次开发库升级 SQL，不直接执行数据库升级。
- 不将未知旧数据批量标为方法或 API，不清空工作库，不替换现有已发布引用。
- 是否收紧 `qualified_name` 唯一约束、如何处置重复或旧关联，待取得限定范围的数据证据后确定；首批不盲目加唯一索引。
- 开发库升级、最终旧入口退场和已有引用处置仍需要对应批次的证据；本决定不代表旧数据问题已解决。

## 2. 接下来的实现顺序

| 子批次 | 与用户任务的关系 | 可交付结果 |
| --- | --- | --- |
| BMAPI-2A | U1/U2 能准确识别自己接入的对象 | 显式资产类型从 SDK 声明到接纳投影可追踪，并有模块验证；不再只能依靠接入方式猜类型 |
| BMAPI-2B | U1/U2 找到并看懂业务方法 | 独立业务方法读模型、目录与详情，必要目录读取兼容性限于该路径；复用参数、来源、状态和引用展示 |
| BMAPI-2C | U1/U2 在明确身份与环境下试用 | 受控单项试调用、错误定位和 Run/Trace；不要求人为建 MCP 发布 |
| BMAPI-2D | U2 将方法用于真实 Workflow | 选择与输入输出映射、调试/发布、真实执行与引用验证；这里才验收首个完整纵向路径 |

这是 BMAPI-2 内部的小步实施，不将 BMAPI-2A 的基础改动计为完整业务方法交付。每个子批次结束由主任务复核后下发下一批。
