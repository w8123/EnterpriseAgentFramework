本专项的目标、范围、用户任务和完成条件以本文为统一依据；当前执行位置与证据只记在[实施进度](./业务方法与API重构实施进度.md)。根目录 [AGENTS.md](../../AGENTS.md) 是开始和恢复任务的规则入口。

- 已确认目标决定要实现什么；真实代码、SQL、接口与运行结果说明现在实现到哪里。不能把目标写成现状，也不能因旧实现不同而取消目标。
- 后续会话先读本文和实施进度，再检查当前工作树。聊天摘要、旧计划、提交说明只提供上下文。
- 仅调整实现细节时，执行者依据代码和契约自主决定，记录原因；改变已确认产品边界时，先整理具体方案、影响和取舍，再与用户讨论。
- 同一范围只有一个当前执行批次。每批完成后回写证据和下一步，不依靠聊天记忆恢复工作。

| 编号 | 已确认决定 | 实施含义 |
| --- | --- | --- |

| D2 | 明确建设“业务方法”模块，与 API 分别管理 | 注解方法描述接入机制；业务方法描述明确开放的 Java 业务操作 |

“Capability / 能力”可继续作为统称、聚合视图或服务技术身份；本专项不把它另建成与业务方法、API 重复维护的第三套资产。

## 3. 产品对象与职责

| 对象 | 拥有的职责 | 明确边界 |
| --- | --- | --- |
| 业务方法 | 明确开放的 Java 业务操作、稳定身份、业务说明、输入输出、来源与调用条件 | 不等同于所有 Java 方法；方法内部业务逻辑仍由业务系统负责 |
| API | 明确的 HTTP 请求与响应操作、来源、版本与接入条件 | Controller 与 OpenAPI 是其来源；无需为使用 API 人工复制一条业务方法 |
| 发现与同步机制 | 发现候选、解析契约、同步变化、维护来源证据 | 不成为新的用户维护目录；不能自动赋予调用权限 |
| 调用投影 | 将源资产转换为 Runtime、Workflow 或开放协议可消费的定义 | 从源资产及其契约生成，不能成为第二处事实源 |
| Workflow | 跨步骤、变量映射、条件、异常处理、独立版本与运行证据 | GraphSpec 是执行语义；本专项不另造方法组合 DSL |

分类应由对外契约决定。业务方法可以经 SDK 的 HTTP 入口传输；SDK 也可以发现 HTTP API。不得单靠 `source=sdk`、是否有注解或是否走 HTTP 推断类型。

当前 Agent 仍通过已发布配置与 Workflow-as-Tool 路径消费 Workflow。本专项的基础使用路径是方法 / API 进入 Workflow，不隐含增加 Agent 直接绑定任意方法的运行能力。

## 4. 两类用户必须完成的任务

以下是目标任务，尚未验收。示例使用隔离开发环境与测试数据。

### U1：Java 开发者接入并维护业务方法

1. 在已接入项目中声明一个查询方法及其参数，启动业务实例并同步。
2. 在业务方法中找到正确对象，核对稳定身份、项目、来源、输入输出和当前调用条件。
3. 不再人工建立或搬运一份通用 Tool 定义；允许自动接受的变化自动完成，需要业务判断的例外有明确原因。
4. 在明确的测试身份与环境中试调用，看到真实返回或可定位的失败原因。
5. 修改输入契约或移除来源后，能看到具体影响；已有引用按既定契约受保护，处理变化后可再次验证。

### U2：实施人员使用业务方法

1. 按项目和业务用途找到方法，理解适用范围与操作影响。
2. 看懂必填字段、参数来源与返回字段；示例来自可信声明或验证结果，生成示例明确标注，不伪造真实业务数据。
3. 完成一次试调用；失败时能区分参数错误、来源不可用、权限不足和契约变化。
4. 将该方法用于 Workflow，完成输入映射和返回字段引用，调试后在 Trace 中关联到同一源资产。
5. 从方法详情看到使用位置与变化影响；未知或不完整的引用证据明确显示为未知。

### U3：开发者与实施人员接入并使用 API

1. 通过 Controller 扫描或 OpenAPI 导入发现接口，在 API 管理中核对请求与响应契约。
2. 配置必要接入条件并完成真实 HTTP 验证；API 市场的收录或项目接入意图不能代替验证成功。
3. 在 Workflow 中选择 API、映射输入输出并完成调试，无需将其改名或复制为业务方法。
4. 同一接口从多种来源发现时，有明确的身份关联、来源优先级和冲突解释；不同项目、服务或环境的同名操作不能误合并。

### U4：使用者处理变化与定位影响

1. 修改名称、输入输出、路由或来源状态，能够区分展示变化与执行契约变化。
2. 查看具体 Workflow 草稿、发布版本及已有开放发布的引用；不完整查询不显示“没有使用方”。
3. 变化处理沿用已有来源保护和发布契约；目录接纳不自动改变调用授权或重新发布 MCP / A2A。
4. 新入口完成覆盖后，旧维护入口停止制造重复定义，并提供明确去向。

## 6. 实现前必须收敛的设计问题

BMAPI-1 只做与 U1–U4 直接相关的映射和设计。每项应补充代码证据、选定方案、影响面和回归场景。可由现有契约推导的常规选择由执行者处理；无法推导且改变业务边界的选择再与用户讨论。

| 编号 | 待收敛问题 | 产出要求 |
| --- | --- | --- |
| Q1 | Controller 同时有 HTTP 映射与方法注解时，声明的是补充 API 元数据还是独立调用入口？ | 两种意图的表达与分类规则；解决当前 MVC 扫描跳过显式注解方法的行为；不得静默丢失身份或自动制造重复对象 |
| Q2 | 方法与 API 的稳定身份、版本、来源、调用投影怎样关联？ | 领域模型、字段所有权、唯一性、路由及引用映射；包括跨项目同名、多来源同 API、契约变化 |
| Q3 | 哪些字段由业务来源维护，哪些由平台维护？ | 注解 / 文档 / 平台补充的优先级、冲突与回写规则；不能出现两处自由编辑同一契约 |
| Q4 | 试调用如何复用现有真实执行链路？ | 环境、身份、输入、返回、Trace 与错误契约；写操作说明真实影响；保持原有 ACL 与来源保护 |
| Q5 | 当前扫描目录、外部 API 项目接入和调用投影怎样收口？ | 每种现有对象的保留、改造、合并或退场清单；目录收录、配置完成与验证成功分别表达 |
| Q6 | 当前开发数据和已发布引用如何处理？ | 基于实际使用情况选择重建、升级或显式映射；新库直接体现正确模型，不为假想旧数据建设复杂兼容层 |

这些问题是待完成的设计工作，不是对已确认目标的再次投票，也不是恢复旧平台治理大计划的理由。

按用户任务组织批次，允许一个批次涉及前后端和 SQL。批次过大时按可验证场景继续拆小，每个子批次仍标明 U 编号与完成条件。

| 批次 | 交付目标 | 完成条件 |
| --- | --- | --- |
| BMAPI-0 | 固定方向和恢复入口 | 本文、进度表、命名规则与索引一致；文档检查通过 |

## 8. 防止范围偏移的执行规则

1. **每项改动对应用户任务。** 说明它服务 U1–U4 的哪一步，以及改动前后用户会看到什么结果。
2. **支撑工作必须有具体阻塞证据。** 范围、权限、导航、公共组件等变更，应指出哪个场景被哪个现有行为阻塞，并限定最小修改范围；无法关联的改进放入后续事项。
3. **同一事实只维护一次。** 来源契约、资产身份、调用投影、执行记录各有 owner；聚合页面不形成第二套可写事实源。
4. **旧入口有退场条件。** 每个替代入口记录消费者、接替实现、回归证据与退场批次；不得无限期双写或保留两个同义管理模块。
5. **普通实现选择自主推进。** 不把每次拆类、字段命名、组件复用变成用户审批；先完成证据核对和可审查方案。
6. **产品边界变更先记录影响。** 新增独立业务对象、另一套编排或执行机制、改变调用授权含义、扩大成全平台改造时，暂停相关改动，与用户讨论具体取舍；已授权且不依赖该选择的工作可以继续。
7. **目标变化要留决策记录。** 写清原决定、证据、新决定、影响批次和用户确认位置；旧结论标为被替代，不暗改目标或完成标准。
8. **恢复任务先核对状态。** 阅读基线和进度、检查 Git 与相关代码，处理“记录与现状不同”；不能照着旧 TODO 或聊天最后一句直接续做。

明确不作为本专项独立交付：全站项目范围改造、通用 RBAC 重写、Agent / Workflow 全页面整理、新增微服务、全局品牌替换、另建方法组合语言、Agent 直接任意方法调用、API 市场扩建、真实权限变更与部署。若其中某点确实阻塞 U1–U4，按上述依赖规则缩小范围后处理。

## 9. 验证与完成的证据标准

- 静态、模块测试、浏览器任务走查、真实业务调用分别记录。模拟 API 或组件测试不能代替真实 SDK / HTTP 调用。
- 后端执行相关模块编译或目标测试；前端执行目标验证与构建，并走查正常、失败、空态、窄视口与关键键盘操作。
- 模型或 SQL 变化同步维护 `sql/initV2.sql` 和服务表所有权；需要升级当前开发 / 测试库时提供当次 upgrade SQL 与执行说明。
- 涉及跨服务或引用变化时运行相关架构守卫；检查通过只说明守卫覆盖的规则成立。
- 真实验收至少覆盖：只读方法、写方法的受控测试、Controller API、OpenAPI API、双重声明、多来源同接口、跨项目同名、契约变化及来源移除。具体夹具和期望行为在 BMAPI-1 固定。
- 每份证据写明批次、日期、版本或工作树状态、环境、身份类型、场景、命令 / 操作、实际结果和材料路径；不记录凭据。
- 无环境、无真实身份、无外部依赖或未做用户实测时写明缺口。代码完成、验证完成和用户易用性结论分别表达，不伪造通过。
- 最终确认两个角色都能完成 U1–U4 对应任务，同时核对旧入口退场清单。新增资产模型、仅能浏览或只完成方法路径而漏掉 API，均不算专项完成。

> 继续业务方法与 API 重构。先读 AGENTS.md、docs/plans/业务方法与API重构实施基线.md 和 docs/plans/业务方法与API重构实施进度.md，核对当前工作树与证据，再从进度表的下一步推进。每项改动关联用户任务，保护已有 WIP，完成一批后更新验证结果和下一步；不要自动恢复旧平台治理批次。
