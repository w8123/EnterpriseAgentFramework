# 记忆模块重设计方案

> 状态：已确认（2026-10-17）；M1–M4 已实施。依据：[平台定位与架构总览](../01-平台定位与架构总览.md) 中已确认的产品框架。
> 按 M1–M4 分批实施，每批独立 PR、合入 `dev` 并部署验证。

## 结论

记忆不再是独立产品模块，而是 **Agent 的一项能力**：实施人员在 Agent 配置里决定是否启用、记什么；终端用户在嵌入式对话里查看和管理自己的记忆。现有五层概念收拢为用户可见的两类记忆，加一项改名后归入业务能力的「业务索引回源」。

## 现状问题（代码证据）

| 问题 | 证据 | 影响 |
| --- | --- | --- |
| 记忆对所有 Agent 一刀切 | `PersonalMemoryRecallService.recall` 只看身份来源（`AGENT` / `EMBED_SESSION`），不看 Agent 配置；`runtime_agent_config_version` 没有任何记忆字段 | 实施人员无法决定某个 Agent 用不用记忆 |
| 终端用户看不到自己的记忆 | 嵌入式对话（`EMBED_SESSION`）会召回记忆、也会提取候选；但管理接口 `/api/context/personal-memories/**` 只认平台登录会话（`PersonalMemoryIdentityResolver.resolve`），`/api/embed/**` 没有记忆接口 | 终端用户的候选无人确认、记忆无法自助删除 |
| 入口放错地方 | 「我的记忆」「跨域记忆擦除」挂在「身份与权限」（`sidebarMenu.ts`） | 与产品框架冲突 |
| 数据模型是上下文治理遗留 | `control_context_item` 带 `memory_lane=PROJECT_DEV`、11 种 `item_type`、`visibility=PROJECT/TENANT/GLOBAL`；个人记忆还要经过 `namespace` / `binding` / `evidence` 三张表 | 一条「记住我喜欢简洁回复」要写 4–5 张表；字段语义大半用不上 |
| 名词混乱 | 「业务记忆」实际是业务索引命中后回业务系统重新读取（`RuntimeBusinessMemoryHydrationService`、SDK `ReachBusinessMemory*`），与记忆无关 | 开发者和实施人员误解 |
| 会话窗口只能全局配置 | `RUNTIME_SESSION_MEMORY_MAX_CONTEXT_MESSAGES` 环境变量 | 不同 Agent 无法按场景调整 |

## 目标模型

| 类别 | 用户看到的 | 谁配置 / 管理 | 事实源（owner） |
| --- | --- | --- | --- |
| 会话记忆 | 同一对话里的多轮上下文 | 实施人员在 Agent 上开关、设窗口轮数；终端用户可清空当前会话 | runtime |
| 个人长期记忆 | 「记住我……」的偏好和事实 | 实施人员决定 Agent 是否读取、是否允许写入；终端用户查看、确认候选、删除 | control（检索投影在 knowledge） |
| 业务索引回源（不叫记忆） | 「查业务」的一种方式 | 开发者在业务能力里声明回源方法 | 业务系统 |

**个人长期记忆归属用户，不归属 Agent。** 同一用户在不同 Agent 间共享；每条记忆记录来源 Agent，用户可按来源筛选。Agent 只决定自己是否读、是否写。

### Agent 记忆策略

写入 `runtime_agent_config_version`，随配置版本发布，草稿可改、已发布不可变。

| 配置项 | 取值 | 新建 Agent 默认 |
| --- | --- | --- |
| 会话记忆 | 开 / 关 | 开 |
| 上下文窗口 | 最近 N 条消息（4–100） | 40（沿用当前全局默认） |
| 读取个人记忆 | 开 / 关 | 关 |
| 写入个人记忆 | 关闭 / 仅用户明确要求（「记住……」）/ 明确要求 + 自动候选（需用户确认） | 关闭 |

Runtime 是策略的权威执行方：按本次实际执行的配置版本决定是否持久化会话、窗口大小，以及是否把个人记忆交给 Supervisor，并在响应 `metadata.memoryPolicy` 中回报策略。Control 网关据此决定本轮是否写入个人记忆（`OFF` 不写、`EXPLICIT` 只处理「记住……」、`EXPLICIT_AND_CANDIDATE` 再做自动候选），并按 Agent 短时缓存读取开关，已知不读取的 Agent 不再做召回。不再依赖请求体里的 `useMemory` / `contributeMemory`。

已有配置版本升级后取列默认值：会话行为不变，个人记忆读写关闭，需要的 Agent 在编辑页重新打开并发布。

### 入口

| 入口 | 位置 | 用户 |
| --- | --- | --- |
| Agent 编辑页 · 记忆 | Agent 配置 | 实施人员 |
| 嵌入式对话 · 我的记忆 | `ReachAiChatElement` 面板：列表、来源筛选、确认/拒绝候选、删除、全部清空 | 终端用户 |
| 个人中心 · 我的记忆 | 管理端右上角用户菜单 | 在管理端调试 Agent 的平台用户 |
| 合规 · 跨域数据擦除、会话保留 | 新的「合规」导航分区 | 平台管理员 |

「身份与权限」下不再有记忆入口。

## 数据与接口

按「新库直接重建，不兼容旧数据」规则处理；已有开发/测试库提供 upgrade SQL（个人记忆数据丢弃，已部署环境只有测试数据）。

**新表（control 所有）**

| 表 | 用途 | 替代 |
| --- | --- | --- |
| `control_personal_memory` | 一条记忆：tenant、owner、type（FACT / PREFERENCE / RULE / NOTE）、content、来源 Agent / 会话、时间 | `control_context_namespace` / `item` / `binding` / `evidence` |
| `control_personal_memory_candidate` | 待用户确认的候选 | `control_context_memory_candidate` |
| `control_personal_memory_audit` | 增删改与确认审计（不存正文） | `control_context_audit_event` |
| `control_personal_memory_outbox` | 到 knowledge 检索投影的同步 | `control_context_memory_outbox` |
| `control_runtime_user_mapping` | 平台用户与运行时用户的映射（仅改名） | `control_context_runtime_user_mapping` |

`control_memory_erasure_*`、`runtime_conversation_*`、`runtime_session_retention_*`、`knowledge_personal_memory_index*` 保持不变。

M2 实施时的取舍：

- 保留 `RULE` 类型，因为候选提取器会产出「以后都要……」一类规则，归入 NOTE 会丢失语义。
- 删除即物理删除，记忆没有状态列；审计行保留事件但抹掉记忆 ID、会话和 trace。重复删除返回 404。
- 去重靠 `(tenant, owner, content_sha256)` 和 `(tenant, owner, semantic_key)` 唯一键，取代原来的 namespace 行锁。
- 请求体里的 `useMemory`、`contributeMemory` 开关删除，是否召回、提取只由 M1 的 Agent 记忆策略决定。
- 权限码 `context:memory:erasure:manage`、`context:runtime-user:mapping:manage` 属于技术身份，不改名。
- 升级脚本直接丢弃旧个人记忆数据并清空 Knowledge 投影（当前只有开发/测试数据），运行时用户映射改名保留数据。

M3 实施：`/api/embed/memories/**` 的所有者只取自已验证的嵌入 token（tenant + externalUserId，缺省 globalUserId），与嵌入对话召回、写入使用的身份一致；`EmbedChatHost` 右上角提供「我的记忆」入口，`createEafChat({ memories: false })` 可关闭。终端用户面板只做查看、删除、确认 / 忽略候选和全部清空，不提供手动新增（对助手说「请记住……」即可）。

**接口**

| 新接口 | 身份 | 替代 |
| --- | --- | --- |
| `/api/me/memories/**` | 平台登录会话 | `/api/context/personal-memories/**`、`/api/context/personal-memory-candidates/**` |
| `/api/embed/memories/**` | 嵌入会话 token | 新增 |
| `/api/compliance/erasure-requests/**` | 平台登录 + 擦除权限 | `/api/context/memory-erasure-requests/**` |
| `/api/runtime-user-mappings/**` | 平台登录 + 权限 | `/api/context/runtime-user-mappings/**` |

**代码**

- `control/context` 包拆为 `control/memory`（个人记忆、候选、召回、outbox）、`control/compliance`（跨域擦除）、`control/identity`（运行时用户映射）。
- 个人记忆服务按新表重写，预计从约 3700 行（`control/context` 中个人记忆相关类，不含擦除和用户映射）收缩到一半以内；去掉 namespace / binding / evidence 和 `memory_lane`、`visibility`、`trust_level` 等未用语义。
- `BusinessMemory*`（SDK、`ai-runtime-contract`、runtime、knowledge）改名为 `BusinessIndexResolution*`。SDK 公开类改名属于破坏性变更，在 starter 版本说明里写明。

## 分批实施

| 批次 | 内容 | 用户可见结果 | 验收 |
| --- | --- | --- | --- |
| M1 Agent 记忆策略 | 配置版本增加记忆字段；Agent 编辑页「记忆」区；Control 网关按策略召回 / 提取；Runtime 按策略决定会话持久化和窗口 | 实施人员能为每个 Agent 开关记忆 | 两个 Agent 一开一关，同一用户对话，召回与候选行为符合配置；Baota 上 `erp-assistant` 验证 |
| M2 数据模型与代码收口 | 新表、新包、新接口；删除旧表与 `control/context`；upgrade SQL；更新表所有权文档 | 管理端「我的记忆」移到个人中心，「合规」分区上线 | 控制台增删查、候选确认、跨域擦除全链路；`service-table-ownership` 校验通过 |
| M3 终端用户自助 | `/api/embed/memories/**`；嵌入式对话「我的记忆」面板 | 终端用户在业务系统里管理自己的记忆 | 芋道 ERP 嵌入对话里说「记住……」，在面板看到并删除，再对话不再召回 |
| M4 名词收口 | 业务索引回源改名；重写 `docs/architecture/personal-agent-memory.md` 为面向用户的说明 | 文档与界面不再出现「业务记忆」 | 全仓 `rg -i "business.?memory"` 只剩改名说明 |

M1 先做，因为它不依赖表结构调整、立刻解决「一刀切」问题；M2 与 M3 依次进行，M4 可与 M3 并行。

## 不在本方案内

- 不替换检索投影和 embedding 实现（Knowledge 原生投影 + Model Gateway），也不引入 Mem0 / ReMe / Graphiti。
- 不改会话保留、Legal Hold 和会话擦除的机制，只调整入口。
- 不做按项目或租户共享的团队记忆；如需要，另立方案。

- Java 类型、包和契约统一改名：`BusinessMemory*` → `BusinessIndex*`（契约包 `runtime.contract.bizindex`、SDK 包 `reach.sdk.bizindex`、Runtime `runtime.bizindex`），schema `reachai-business-index-{reference,resolution}-v1`，Runtime 配置 `business-index.*` / `RUNTIME_BUSINESS_INDEX_*`，索引字段 `agent_reference_enabled`（升级脚本 `sql/upgrade-20261017-business-index-reference-naming.sql`）。实现了 resolver 的业务系统需要按新包名重新编译。
- `docs/architecture/personal-agent-memory.md` 重写为面向实施人员和终端用户的说明；业务索引回源契约移到 `docs/architecture/business-index-resolution.md`。
- 剩余 `business.?memory` 只出现在本方案、历史迁移文件名和改名说明里。
