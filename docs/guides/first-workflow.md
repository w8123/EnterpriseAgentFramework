# 创建第一个 Workflow

以「按订单编号查询订单」为例，完成从业务能力到已发布流程的最小闭环。先使用只读操作，便于核对身份、字段映射和执行结果。

## 前提

- 已按[系统接入](../integration.md)接入查询方法或 HTTP API，并接纳其当前契约。
- 目标项目的试调用已通过，账号具有流程编辑、调试和发布所需权限。
- 若流程使用模型，已[接入并测试模型](model-setup.md)。

示例中的订单编号是你自己业务系统的测试数据，节点与字段以能力实际返回的契约为准。

## 1. 确认输入与结果

在业务能力目录找到目标查询操作，查看输入、响应结构、副作用和来源状态。先完成一次受控试调用，记录真正需要映射的字段路径。

例如实际响应为：

```json
{
  "success": true,
  "data": {
    "orderId": "demo-order",
    "status": "待处理"
  }
}
```

订单状态的路径就是 `data.status`。不要根据页面显示的摘要把它误写成 `status`。

## 2. 创建并编排

1. 在「Workflow」创建属于目标项目的草稿，进入 Studio。
2. 声明流程输入，例如必填的订单编号。
3. 添加对应的业务方法或 HTTP API 节点，从目录选择真实目标。
4. 将流程输入映射到操作的参数，将实际返回字段映射到流程输出。
5. 连接入口、查询与输出，补充为空和失败时的结果处理。

画布负责布局，GraphSpec 保存执行语义。不要只靠画布连线外观判断分支与错误处理已经配置正确。

## 3. 保存、校验与调试

保存当前工作副本，运行发布校验，逐项处理错误。符合当前策略的只读流程可以使用整稿只读试运行；它使用项目测试身份，不代表员工的真实业务身份。

检查输入、调用目标、返回数据和 Trace。请求超时或结果未知时先查询原执行记录，不要用重发写调用排查问题。

如果提示草稿冲突，保留自己的修改，重新读取并比较后再保存。具体调试边界见 [Workflow 编辑与调试](../workflow.md#编辑与调试)。

## 4. 发布并交给 Agent

发布校验通过后发布 Workflow，记录新版本。再进入目标 Agent 的配置，把这个已发布流程加入可调用范围，保存并发布 Agent 配置。

Workflow 发布与 Agent 配置发布是两步；Agent 使用固定的发布版本。以后修改流程，需显式发布并更新引用，不会自动替换已有线上版本。

## 5. 验证一次真实使用

从目标使用入口提问，确认助手调用了预期流程、业务系统看到了正确身份，并在运行中心回查同一次 Run / Trace。分别测试有结果、无结果、无权限和业务异常。

接入员工入口见[页面对话](embed-chat.md)和[员工 AI 工具](employee-ai-tools.md)。发布、来源变化与恢复规则见[业务能力与 Workflow](../workflow.md)。
